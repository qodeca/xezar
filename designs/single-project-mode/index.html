Single-project mode – UI design

xezar can keep every setting, account and working file inside one repository folder, so a clone runs the same way with no host setup. The cockpit has to answer one question the moment it opens — "is this xezar the one that lives in this repository?" — and then stop offering the four affordances that only make sense when it serves several projects. This design is that answer: one neutral badge, one line per Settings section naming the file it writes, one new content state for an account whose folder is not on this machine, and three removals.

Status: draft for design review (xezar-ux-design, authoring mode). Static mockup, not shipped code. Tokens and type come from docs/design-system/cockpit.css, which mirrors packages/web/src/styles/index.css. Covers the cockpit slice (PR4) of qodeca/xezar#600. Design decisions

DecisionChoiceWhy
Where the badge livesThe sidebar brand block, on its own second line; the mobile-status slot on a phoneThere is no cockpit header in xezar. The brand block is where the cockpit already says what it is, and a second line means the badge never competes with the repo/branch chip for 264 px — so neither has to truncate.
Badge colourNone of its own: Badge variant="outline", text-muted-foregroundViolet means "a person is wanted" and danger is the development build's. A third colour in one row would teach two meanings for one place. The words carry the meaning; the folder icon reinforces.
Badge words"Single project"The same name as the --single-project flag, the boot line and the guides. Three names for one thing is how a mode becomes folklore.
Both badges at onceDev badge on the tile corner, mode badge inline — neither movesThey answer different questions ("built from source" against "state lives here"). Stacking them in one place would make each harder to read and would push one of them off the row.
Nothing before health answersNo badge, no placeholder, no reserved gapA badge that guessed "global" and corrected itself 200 ms later would claim a fact it did not have — the same rule the setup surface follows for "observed is not checked".
File naming grainOne line per section, under the description; not per fieldA pane's fields all land in one file. Five repeats of one path stop being read. A field that genuinely writes elsewhere says so in its own hint.
File-note wording"Saved in this project — <file>." plus, where true, "It is committed, so a clone starts with these …"The file name alone answers "where"; the second clause answers the question a person actually has, which is whether their colleague gets this too.
Global mode keeps no file noteThe line renders in the mode onlyIt answers a question only the mode raises. Adding it everywhere would change the default path for every existing user to no benefit.
Scope chip"Workspace settings" replaces "Global settings" in the modeIn the mode those settings are committed to one repository. Calling them global would be the one word on the screen that is false.
The unavailable accountA danger dot, the word "Unavailable", and one sentence naming the path and the remedyColour never carries it; the sentence does. The same string is the refusal a task gets, so the two are recognisably one fact rather than two bug reports.
Hosted mode lists accountsRead-only list, every write hidden, one sentence saying who can actThe accounts are committed project state now, so a hosted reader can legitimately see which logins the work expects — and that one is missing. Every write stays refused; the 409 that closed a hooks-based path is untouched.
Removals are absencesAdd project, the project pill and the Projects group are not rendered, not disabledA disabled control invites a click that can never work, and a picker whose only option is the current one offers nothing. There is no honest enabled state for any of the three.
The refused registry pageAn explanation, with "Back to settings"The page exists in this build; the mode took it away. "Page not found" would be false and would teach a person to doubt their own bookmark. Named as OD-1 because it also changes the answer for the XEZ_SINGLE_PROJECT=1 narrowing.
No import dialogThe import ask stays in the terminalThe ask happens on the first run with the flag, which is a command-line event. A cockpit dialog would be a second surface with its own six states for a question asked once, ever.

Accessibility checklist for the build

  • The badge is text, not colour: "Single project" plus an sr-only tail naming the consequence. Its folder icon is aria-hidden.
  • The badge is not interactive and is not in the tab order — there is nothing to change about it from the cockpit, because the folder decides.
  • Every removal is an absence, so no disabled control has to be explained and nothing focusable is dead.
  • The unavailable account carries a danger dot and the word "Unavailable" and a sentence; any one of the three alone would be enough to act on.
  • The refusal a task gets is role="alert"; the hosted-mode notice is role="status", because nothing is broken.
  • Loading lines and skeleton blocks are role="status"; the mode badge is never a skeleton, because its absence is meaningful.
  • The file note is ordinary text in the section's own heading block, read after the description by a screen reader in the order it is read visually.
  • Touch targets are 44 px on phone at every density, including the Connect and Show details buttons on a stacked account row.
  • Both themes work through tokens only, with no dark: variant and no raw colour.
