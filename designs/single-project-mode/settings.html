Settings names the file it writes

In the mode every setting is written into the repository, so "will this travel to my colleague's clone?" becomes a real question on every pane — and the honest answer is the file name. One line per section, under the section description, in the section's own words. The line appears only in the mode: in global mode the panes are unchanged.

1. A project-scope section

Project sections already describe this repository, so the file name is the only new fact. This one is Agents — which backend and model this project's tasks use when they choose none.

/p/acme-api/settings/agents · single-project mode

Agents

The backend and model a task uses when it picks none.

Agents

Which agent this project's tasks use, and the model each one starts with.

Saved in this project — .xezar/config.json. It is committed, so a clone starts with these settings.

Default agent

The agent a new task starts with. A task can still pick another one in the composer.

Base branch

The branch a task's worktree is cut from. Leave empty to use the repository's own default branch.

Why one line per section, not per field. A pane has three to six fields and they all land in the same file. A line on every field would print the same path five times and stop being read. Where a single field genuinely writes elsewhere, its own hint names that file — the hint is already the place a field explains itself (patterns.md §8).

2. A global-scope section, and the scope chip

This is the pane the mode changes most. Global sections describe the person and the machine, and today a chip in the header says "Global settings" so the two areas are told apart at a glance. In the mode that word is false: nothing here is global any more — it is committed to this repository and it travels with it. The chip says "Workspace settings" instead, and the file note says where.

4. The unavailable account

The only genuinely new content state in the feature. Accounts travel with the repository, so a clone can carry an account whose folder exists on nobody else's machine. xezar boots anyway (FR-6.1), the row says so and names the path (FR-6.2), and any task that asks for that account is refused with the same sentence (FR-6.3). There is no silent fallback to another login — that is the failure this state exists to prevent.

A task that asks for that account is refused with the same sentence — in the task thread, not as a toast, because it is why the task did not run:

Agent account “Work account” is unavailable — this account's folder does not exist on this machine: ~/.claude-work. Connect signs in and creates it, or pick another account for the task.

One string, two places. The row's sentence and the task's refusal are the same string with the account name prefixed, so a person who reads one recognises the other. It names the path inline even though the row already shows it above, because the refusal a task gets has no row above it to read the path from.

5. What this page does not change

  • The Remove confirm, the Add account dialog and Show details behave exactly as they do today, including the identity exception being on-demand and refused in hosted mode.
  • The discovered account is still listed and still not editable: it is what agentHomePaths() finds, which is a fact, not a setting. It is also not committed — it describes this machine.
  • "Folder not created yet; Connect will make it" stays the wording for an account you just added on this machine. "Unavailable" is for an account the repository carries, and the difference matters: one is a step you have not taken, the other is a machine that cannot honour the project's expectation.
