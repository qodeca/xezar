New issue in the GitHub tab – UI design

A person reading the GitHub tab decides an issue is missing. Today the only way to file one is to leave xezar for github.com, or to write a task by hand and hope it files a good issue. This design adds one control in that tab. It opens a task draft with the issue-create skill and this project already chosen, collects a brief in the person's own words and starts an ordinary task. It files nothing: approval stays with the agent's Create or Revise question in the task.

The one distinction a person must never miss

Starting the task is not filing the issue. Every surface in this design says it in words before it says it in anything else: the dialog's description, a standing note above the footer, the button label Start drafting rather than Create or File, and the strip that reports Drafting an issue while the task runs. Filing happens exactly once, at the agent's Create / Revise question inside the task thread. No colour, icon or tone carries this: remove every colour from the page and the sentences still say it.

Design decisions

DecisionChoiceWhy
PlacementEnd of the GitHub tab's tab row, pushed right, on both the Issues and the Pull requests viewIt is the screen a person is on when they conclude an issue is missing, and the list they just searched is the duplicate check. It costs no nav item, no new route and no keyboard shortcut. It is not a third tab: a tab changes what you are looking at, this starts work.
Second entryThe list's empty state, when the local narrow and the forge search both found nothingThat is the strongest moment in the whole flow — the person has just proved to themselves that the issue does not exist. Offering it there is the only place the duplicate-first rule is free.
Not a routeA Dialog, not /github/new and not the /new composerThe brief is one field. A route change loses the list being read, and the composer asks for a workflow, a runner, variants and a worktree — six decisions for a person who has one sentence to write. The composer stays reachable for anyone who wants those options.
Button labelStart drafting, never Create or FileThe label is the strongest promise on the screen. Create would be a lie: this call starts a task.
The skill is named, not chosenA read-only xezar-issue-create chip plus View skillA picker would invite a person to run something else under a button that says New issue. Naming it keeps the promise inspectable without making it a decision.
Project preselectedThe route's own project, stated as text in the dialogThe GitHub tab is project-scoped already. Showing the destination repository and the project as text, before the box, is what makes the later “file into qodeca/xezar” question unsurprising.
Backend pills keptThe existing EnginePills, exactly as hand-to-agent.tsx uses themEvery other place that starts a task from this tab offers them, and the provider gate ("Connect an agent provider") is already written there. A second grammar for the same choice is a divergence.
Skill unavailable shows the controlThe button stays; the dialog carries the explanation and keeps the briefHiding it turns a missing capability into a missing feature and sends a person looking for a button that exists elsewhere. The dialog names what is lost — template intake, closed-issue duplicate search, the approval step — offers an ordinary task with the same text, and installs nothing.
Hosted mode is not a refusalThe control works; one line names whose GitHub login files the issueStarting a task is not a local-machine capability, so there is no 409 to render. What genuinely differs is that the host machine's gh login is the author. Inventing a refusal would be false; staying silent would be worse.
No gh, no remoteNo control at all; the tab's existing explainer stands unchangedThere is no destination to name, and the header that would carry the button is not rendered on that screen. The skill's local-draft fallback is still reachable from the ordinary composer. Open question OQ-1.
Loading and tab errorNo controlA button that names a repository the cockpit has not read yet would be a guess.
The question has one homeThe strip links to the task; the Create / Revise chips are only in the thread's AskCardTwo places to answer one question is two places that can disagree, and the thread is where the exact title and body being approved are visible. The strip reports; it never answers.
One strip, not a listAt most one issue-draft strip per projectFiling is a single-owner operation in the contract. Several drafts at once is a race the design should not encourage; a second start is still possible and simply replaces what the strip points at.
No “just filed” badgeThe filed issue appears in the list on the next refresh; a stale list says so and offers RefreshA badge held in browser memory would vanish on reload and would claim a list state the tab has not read. Saying “this list was synced before that” is true at every moment.
No new endpointPOST /api/v1/p/:projectId/runs, the call this tab already makesThe contract note and the owner decision both forbid a direct issue-mutation route. The surface adds no server capability at all.
MCP parity in the same PRtask_create with source: {source:'skill', ref:'xezar-issue-create'}Owner rule, 2026-09-16: a new cockpit capability must be reachable by the leader too. The tool already exists and needs no new action — the handoff pins the exact call so the implementation PR ships and tests both.

Accessibility checklist for the build

  • New issue is a real <button> inside the tab row, reached by Tab straight after the two tabs, with the cockpit's :focus-visible ring.
  • Opening the dialog moves focus to the brief textarea; closing it returns focus to the button that opened it. The shipped Dialog does both — do not override onCloseAutoFocus.
  • Escape closes the dialog and the typed brief survives, because the draft is stored, not held in component state.
  • ⌘/Ctrl+Enter starts from inside the textarea, announced through aria-keyshortcuts, exactly as the hand-off box does. A bare Enter inserts a newline.
  • The disabled Start drafting carries its reason as visible text linked by aria-describedby — never a title alone.
  • The draft strip is role="status": it is announced politely when it appears and when it changes to “is asking”, and it never steals focus.
  • A failed start is role="alert" inside the dialog, above the footer, with the brief still on screen.
  • No state is carried by colour: the strip's sentence names the state with the dot removed, and the amber text is --pending-strong, never the soft --pending.
  • Touch targets are 44 px on phone; both themes work through tokens only, with no dark: variant and no raw colour.
