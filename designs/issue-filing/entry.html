The entry, and the draft it opens

One control, in the place a person already is when they decide an issue is missing: the GitHub tab. It opens a task draft, collects a brief and starts an ordinary task. It files nothing.

1. Where the control lives

The GitHub tab's list pane, at its desktop width of 360 px. New issue sits at the end of the tab row, pushed right, so it reads as an action on the list rather than a third tab. It is visible on both the Issues and the Pull requests view, because the decision to file does not depend on which list is open.

2. The second entry: nothing matched

Searching for an issue and finding none is the exact moment a person decides to file one, and it is also the moment the duplicate check has just been done for them. The list's empty state therefore carries the same action a second time. This is the only other place it appears — no nav item, no command-palette entry, no keyboard shortcut of its own.

3. The draft dialog

A dialog, not a page and not a new route: the brief is one field, the person is mid-task in the tab, and a route change would lose the list they were reading. It states the destination before anything is typed, names what will run, and carries one standing sentence that starting is not filing.

4. What happens next, seen from the tab

The dialog closes, a toast confirms, and one strip appears under the tab row for as long as this project has an issue draft running. The strip reports; it never answers. The Create / Revise question is an AskCard in the task thread, which is the one place in the cockpit an agent's question is answered — putting option chips in the GitHub tab would give the same question two homes that can disagree.
