Onboarding – UI design

A person who opens xezar in a new project can already start a task, and nothing tells them that an agent could set the project up first. When xezar itself changes, nothing asks whether the project's own setup still matches. This design adds one discoverable entry for the first setup, one non-blocking notice after xezar changes, and one honest status page that never claims a check it did not do.

The three surfaces

SurfaceWhereWhat it does
Setup entryThe first-task hero on Tasks (primary), plus Settings → Project setup (durable)Starts an ordinary task from the bundled launch definition. Nothing is written until the task previews it and a person accepts.
Post-update offerThe shell's banner row, above the page, below the mobile barOne sentence and exactly two actions: Re-check, Later. It never starts anything by itself.
StatusSettings → Project setupLast observed, last offered, last checked. A manual re-check is always here, dismissed or not.

Design decisions

DecisionChoiceWhy
Primary placementA second, quieter action under the first-task hero on TasksIt is the one screen a fresh project is certain to show, and it is the moment the question "what do I do first" is live. It costs no nav item and no new page. Once a first task exists the hero is gone, which is why the durable home in Settings carries the same entry.
Not the composer's workflow pickerRejected as the primary entryThe picker is only visible once a person is already writing a task, it lists this project's workflows, and a fresh project has none. The setup task still appears in the task list like any other task once it starts.
Hero ranking"Describe a task" stays primary; "Set up this project" is an outline action under a ruleSetup is optional. A person who wants to work must never be made to feel they have to run it first. An independent task is available at all times, with no setup and no MCP.
Durable homeA new project-scope settings section, "Project setup"Status has to live somewhere that survives the empty state, and Settings is where the cockpit already answers "what is this project configured to do". It is a section row, not a nav item.
Offer surfaceThe shell's banner row, role="status", neutral fillA dialog would block, and a toast is gone in five seconds with no way back. The banner row already carries "something about your environment changed", never covers content, and sits in DOM order before the page so it is reached by one Tab.
Offer toneStatus, not alert. Neutral bg-muted/50, no dot, no colourNothing is broken. The alert tone in that row means a provider failed. Reusing it for "a version changed" would teach people to ignore it.
Exactly two actionsRe-check · LaterThe owner's decision Q3. A third action ("Never ask again") would create a state the four-field runtime file cannot honestly hold, and the file is disposable.
No nagLater records the offer for the observed identity; the row does not come back for that identityThe contract's lastOfferedAt is per identity pair. A restart with the same pair is quiet.
Downgrade and dev buildsOne sentence shape for every direction: "changed since this project was last checked"Never "update" or "newer". A downgrade and a development build are changes to inspect, not migration authority.
Missing baselineNo offer at all. The status says "Provenance unknown" and the entry reads as never set upWith no previous bytes, a re-check cannot tell a person's own edits from an older default. Inventing a baseline is the failure this design exists to avoid.
Observed is not checkedThree separate rows, never merged into one "up to date" chipObserving a version proves nothing. Only a finished check advances "Last successfully checked", and a partial or failed check leaves it where it was.
Absent values—The cockpit never prints a fabricated 0 or a guessed date.
No agent backendThe action is disabled with its reason as visible text"Actions with no honest disable reason are hidden, not disabled" – here the reason is honest and useful, so it is shown and wired with aria-describedby.
Hosted modeSetup still runs; one extra line says which part cannot finish hereThe setup task is an ordinary task and works. Registering an agent's MCP file and attaching a leader are local-machine steps. Saying so is more useful than hiding the whole entry. Open question OQ-2.
Never at bootNo task starts without a person or a leader askingA boot-time run would spend money and touch files without consent.

Accessibility checklist for the build

  • The offer row is role="status" with aria-live="polite": it is announced on arrival without stealing focus from the page.
  • Re-check and Later are real <button>s, reached in DOM order before the page body, each with a visible :focus-visible ring.
  • Dismissing moves focus to the page heading, so a keyboard user is never left on a removed element.
  • No state is carried by colour: the offer has no status dot at all, and every state of the entry has its own sentence.
  • The identity rows are a <dl>, so a screen reader pairs each label with its value; — is read as "not recorded" through sr-only text.
  • A disabled action carries its reason as visible text, linked by aria-describedby, never as a title alone.
  • Touch targets are 44 px on phone; the cockpit's h-11 md:h-9 rule.
  • Both themes work through tokens only, with no dark: variant and no raw colour.
