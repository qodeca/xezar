The import block

The block answers one question a person has after setting up a project: “did my accounts come over?” It sits under the pane’s heading, above the problem line and the Defaults card, and it is drawn only in single-project mode. The global layout has nothing to import (the project already reads the personal setup), and hosted mode shows only its refusal sentence, so neither renders the block – not disabled, absent.

The rule that picks the shape: a count above zero gets an action; zero never does (recipes.md: “already-done is not another invitation to mutate”). The card is used once – for the first offer. After the person has answered, the block shrinks to one line, so a decision already made is not asked again in a bigger voice.

1 · unknown, importable = 3 – the first offer (card)

Copy accounts from your personal setup

3 accounts in your personal xezar setup on this machine are not in this project yet. Copying adds their names and config folders to .xezar/agent-accounts.json, which is committed, so everyone who clones this project sees them. Sign-ins stay in their own folders and are never copied.

Or run xezar accounts import-global in a terminal in this folder.

Why a card and why the file name. This is the only state that asks for a decision, and the decision has a cost the person cannot see from here: the names and folder paths land in a committed file. Saying which file, and that clones see it, is the consent the first-run question used to carry. “unknown” is not “you were not asked” – it also covers a project set up before the answer was remembered – so the copy claims nothing about the past. One account reads “1 account in your personal xezar setup on this machine is not in this project yet.” and “Copy 1 account”.

2 · unknown, importable = 0 – nothing to copy (line, no button)

There are no accounts in your personal xezar setup that this project does not already have.

Why a line and not nothing. The sentence is true both when the personal setup has no accounts and when every one is already here, and either way it tells a reader who is looking for missing accounts that the import is not what is missing. It never says “0 accounts”: a count of zero on a button or in a heading reads as a failure.

3 · declined, importable = 3 – the person said no (line, quiet button)

You chose not to copy accounts from your personal xezar setup when this project was set up. 3 can still be copied into .xezar/agent-accounts.json.

Why still offered. A decline at first start is often a decline of the moment (a terminal question at boot), and the later path must exist without a terminal. Why quiet: the answer was No, so the pane does not reopen the pitch – one line, the same button, no card. Declined with importable = 0 reads as state 2: there is nothing left to choose.

4 · done, importable = 0 – copied, nothing new (line)

Accounts were copied from your personal xezar setup — this project has all of them.

4b · done, importable = 2 – copied once, more added there since (line, button)

Accounts were copied from your personal xezar setup. 2 more were added there since and can be copied too.

Why “done” keeps a line. It is the direct answer to “did the import fail?”. The copy is idempotent and merge-only (it adds accounts that are absent and never overwrites a row), so offering it again for new accounts is safe.

5 · copying – the request is in flight

Copy accounts from your personal setup

3 accounts in your personal xezar setup on this machine are not in this project yet. Copying adds their names and config folders to .xezar/agent-accounts.json, which is committed, so everyone who clones this project sees them. Sign-ins stay in their own folders and are never copied.

Or run xezar accounts import-global in a terminal in this folder.

6 · copied – toast, then the block becomes state 4 and is announced

Copied 3 accounts
Copied 2 accounts — 1 was already in this project
Nothing new to copy — this project already has every account

The toast reports what the server did, not what was asked (writing.md §13). The three shapes come from the server’s added/kept counts. The block re-renders from the refetched state; the live region inside it (role="status" aria-live="polite" aria-atomic="true") reads the new line once.

7 · the copy failed – danger toast in the server’s words; the block is unchanged

Could not read your personal xezar setup — ~/.xezar/agent-accounts.json is not a regular file
Agent accounts are managed from the machine that owns the checkout — this cockpit runs in hosted mode.

No new error copy. Both lines are examples of server messages shown verbatim (patterns.md §6, “Mutation error”); the second is the hosted refusal arriving as a 409 if the mode changed under an open page. The button re-enables and the count stays as it was – a failed copy never shows as done.

8 · the state has not arrived yet (only if it is fetched apart from the listing)

Checking for accounts to copy…

Prefer none. If globalImport rides on the accounts listing, the pane’s own “Loading agent accounts…” covers it and this line never shows. If the field is absent from a response (an older engine), the block is not rendered at all – absence is not “unknown”.
