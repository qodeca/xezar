# Guidance for `packages/xezar/src/workspace/`

These rules are the full task-routing guidance moved from the repository root. Root `AGENTS.md` retains the routing index and canonical cross-repository rules.

## Workspace registry / per-user state (`~/.xezar/`)

`~/.xezar/config.json` is the per-user workspace config **and** the project registry — every repo xezar has been booted in (spec `2026-07-20-multi-project-workspace`). **Where state lives is resolved once, in `packages/xezar/src/state-layout.ts`, and nowhere else** (#600): `activeStateLayout()` answers `~/.xezar` (or `XEZ_HOME`) in the default global layout and `<project>/.xezar` in single-project mode, with working files and the skills cache under `<project>/.local/xezar`. Every path goes through that resolver — `xezarHomeDir()` for the per-user home, `xezCacheDir()` for the cache, `agentHomePaths()` for the agent config dirs — so `XEZ_HOME` keeps tests and containers off a real home and a folder that owns its state never reaches the machine's. Never re-derive `homedir()` or join `'.xezar'` at a call site: `state-path-scan.test.ts` reads the source text of `packages/xezar/src` and fails by file and line, with an allowlist that takes a written reason and nothing less. The premortem failure this defends is half-isolation — one forgotten path still reading the shared home while everything says the mode is on. Schema rules are load-bearing: every field optional with `.catch`, `.passthrough()` at every object level, per-entry salvage for `projects` (one bad row never evicts the registry), and writes only through `mergeWriteWorkspaceConfig` (read-modify-write + atomic tmp/rename, `0600`) so two processes converge. A corrupt or read-only home degrades to in-memory defaults with ONE warning — never a boot failure. Migrations are config-files-only, idempotent, additive and non-blocking; run state never migrates. `resources` is the workspace-wide, ENFORCED copy: `maxParallel`, `maxMonitoringSessions`, `monitoringWakeIntervalMinutes`, `autoResumeOnUsageLimit` (default ON), `idleTimeoutMinutes`, `memoryLimitMb`, `worktreeRetentionDefault`, `gateSlots`. The per-repo keys are imported once by migration 001, and what happens next differs per key — do not generalize from one to the other. Per-repo `maxParallel` stops driving enforcement (a registry entry's own `maxParallel` is what narrows the workspace cap), while per-repo `memoryLimitMb` IS consulted again (B2): `WorkspaceSemaphore.projectMemoryLimitMb(repoRoot)` lets a repo override the workspace ceiling for its own runs, the same more-specific-wins lookup `projectMaxParallel` uses. Two absent-key defaults are load-bearing and neither is `null`: `memoryLimitMb` absent now derives a host-sized ceiling (`deriveDefaultMemoryLimitMb`, `floor(totalMiB * 0.6 / 2)` clamped to [1024, 8192] MiB) and `idleTimeoutMinutes` absent reads as 15 — an explicit on-disk `null` still means "no limit" / "never close an idle session", because zod's `.default()` fills `undefined` only. That absent-vs-explicit-null distinction is the whole safety of changing either default; preserve it. `gateSlots` (#672 — how many gate runs may hold the machine-wide gate lease at once) is the third absent-key default and the one with NO `null` at all: absent derives 1, "never binds" is a high number rather than an absence, and it is stored `.optional()` instead of `.default(1)` so an unrelated settings write does not materialise a stored count the user never chose. Its lock files are the one piece of this feature that deliberately does NOT go through the resolver — `<home>/.cache/xez/gate-slots/`, in every layout, because the contention it bounds is one machine's, not one project's (`core/gate-lease.ts`, allowlisted by name in `state-path-scan.test.ts`). Two more stored keys live at the TOP level rather than under `resources` — `followups` and `agentEnvPassthrough`, the counterparts of `XEZ_FOLLOWUPS` / `XEZ_ENV_PASSTHROUGH`: stored wins, absent inherits the env, and `agentEnvPassthrough: []` is a real "forward nothing" and never a clear. "Is the inbox on" is resolved ONCE in the semaphore and threaded into `resolveCapabilities` as an argument rather than re-read, so two spellings of it cannot disagree. Registration is suppressed for task worktrees and `$HOME` itself (`shouldRegisterProject`). A merge-write resolves its path ONCE and uses it for both halves — resolving it twice let a `XEZ_HOME` that changed mid-flight read one home and write another, wiping the user's registry. Two guards back that up: `assertXezarHomeWriteIsSandboxed` refuses any write into the real `~/.xezar` from a vitest process, and `packages/xezar/vitest.setup.ts` pins `XEZ_HOME` to a per-worker sandbox so no case ever runs unpinned. Every write that leaves projects behind also snapshots `config.json.bak`, which `loadWorkspaceConfig` restores from when the config is missing, empty or corrupt (a config that parses and is simply empty is the user's own state and is never overridden). | **Agent accounts** (spec `2026-07-29-agent-profiles`) live in this directory too, but in their OWN file — `~/.xezar/agent-accounts.json`, never a key in `config.json`, so a xezar that has never heard of accounts cannot drop them; `src/workspace/agent-accounts.ts` owns the store, `src/core/agent-profiles.ts` the vendor knowledge and `src/workspace/agent-profiles.ts` the resolution.
