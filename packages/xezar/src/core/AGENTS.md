# Guidance for `packages/xezar/src/core/`

These rules are the full task-routing guidance moved from the repository root. Root `AGENTS.md` retains the routing index and canonical cross-repository rules.

## Agent runners / backends

One seam: every backend implements `AgentRunner`/`AgentSession` and emits both the v1 `AgentEvent` stream and the normalized v2 `UiEvent` protocol. **Read `AGENT_PROTOCOL.md` first — it is the contract a new runner must satisfy** (the event schema, per-backend mapping, golden-fixture testing, and the backend-parity requirement), with an explicit new-runner checklist. New backends slot in as one class — do not leak backend-specific types past the seam. `claude-cli` is a legacy backend id kept so old run records parse. `XEZ_DRY_RUN=1` must keep working (bundled mock, no real CLI). Tool access goes through `allowedTools`, but the zero-config default includes unrestricted `Bash` (no `bashAllowlist`) — see pre-rename issue 430. A step is **read-only** when its resolved `allowedTools` names neither `Edit` nor `Write` (`isReadOnlyStep` in `read-only-lock.ts`, #849/#863 — the one signal; no step key, no `XEZ_*` var), and each backend treats it differently: Claude Code **ENFORCED** (`--disallowedTools Edit,Write,NotebookEdit` removes the tools and `--setting-sources user` keeps project/local settings, hooks and skills from re-widening Bash; Claude's OWN matcher enforces `Bash(<entry>:*)`, so the shared parser and argument table do not apply there until a hook calls them); Codex **CONFINED + command-locked** (the thread starts and resumes in `sandbox: workspace-write` with `sandbox_workspace_write = { network_access: true, writable_roots: <the run's additionalDirectories> }`, so writes are limited to the worktree and run directories while the network stays on; `XEZ_CODEX_NETWORK=0` still turns it off. On a read-only step with `bashAllowlist` present, a shipped `PreToolUse` handler adapts Bash and `apply_patch` payloads to `read-only-lock.ts`; Bash uses the shared command decision and `apply_patch` reaches its tool-name refusal. The runner registers it on start and resume, obtains Codex's normalized key/hash through `hooks/list`, grants that exact trust with `config/batchWrite`, verifies it before turn 1 and fails closed on any gap. A blocked hook's shared reason is persisted as a v1 `note`. Codex 0.155.1 does not discover request-body hooks alone, so the identical generic handler is also idempotently installed in the active profile's user `hooks.json`; it is inert without xezar's process-local allowlist. The worktree and branch remain writable through other non-shell tools, and MCP tools stay under #324 scoping); pi maps the list onto its own `--tools`, so edit/write are absent and `bash` stays — with a `bashAllowlist`, its thin adapter calls `read-only-lock.ts`, which refuses every word the shell would still expand, applies checked argument rows through one program-keyed dispatcher, never permits `sed` or `awk`, and otherwise accepts one simple prefix-matched command; its sole compound exception is the exact two-part verdict-packet pipe. pi alone retains flag parsing, denial-stream shape and the separate worktree guard; `[]` removes bash, and a missing worktree flag fails closed; OpenCode **NOT APPLIED** (it ignores `allowedTools` entirely). Plain `Bash` on a read-only step can still write through allowed commands; a `bashAllowlist` narrows it on all three supported adapters, with the shared parser applying on Codex and pi. A Codex run gets only the MCP servers the project's own `.codex/config.toml` declares: the runner asks the app-server (`config/read`) and switches off home-config servers, plugins, apps and xezar's bridge per thread, failing closed when it cannot ask (#324, `codex-run-isolation.ts`).
