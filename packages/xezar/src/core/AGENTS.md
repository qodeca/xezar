# Guidance for `packages/xezar/src/core/`

Cross-repository rules and the task-routing index are in the root `AGENTS.md`.

## Agent runners / backends

One seam: every backend implements `AgentRunner`/`AgentSession` and emits both the v1 `AgentEvent` stream and the normalized v2 `UiEvent` protocol. **Read `AGENT_PROTOCOL.md` first — it is the contract a new runner must satisfy** (the event schema, per-backend mapping, golden-fixture testing, and the backend-parity requirement), with an explicit new-runner checklist. New backends slot in as one class — do not leak backend-specific types past the seam. `claude-cli` is a legacy backend id kept so old run records parse. `XEZ_DRY_RUN=1` must keep working (bundled mock, no real CLI). Tool access goes through `allowedTools`, but the zero-config default includes unrestricted `Bash` (no `bashAllowlist`) — see pre-rename issue 430. A step is **read-only** when its resolved `allowedTools` names neither `Edit` nor `Write` (`isReadOnlyStep` in `read-only-lock.ts`, #849/#863 — the one signal; no step key, no `XEZ_*` var), and each backend treats it differently: Claude Code **ENFORCED** (`--disallowedTools Edit,Write,NotebookEdit` removes the tools and `--setting-sources user` keeps project/local settings, hooks and skills from re-widening Bash; the only settings a read-only step adds is a step's own `claudeSettings` file, which the engine pins from the base commit and validates to hold `hooks` only, passed as `--settings` (#1001, `workflows/claude-step-settings.ts`); Claude's OWN matcher enforces `Bash(<entry>:*)`, so the shared parser and argument table do not apply there until a hook calls them); Codex **CONFINED + command-locked** (the thread starts and resumes in `sandbox: workspace-write` with `sandbox_workspace_write = { network_access: true, writable_roots: <the run's additionalDirectories> }`, so writes are limited to the worktree and run directories while the network stays on; `XEZ_CODEX_NETWORK=0` still turns it off. On win32 every `workspace-write` thread also sets `windows.sandbox = "unelevated"` (`codexWindowsSandboxConfig`, #1009): without it Codex silently runs the thread `read-only`, and under `approvalPolicy: never` that refuses every command. On a read-only step with `bashAllowlist` present, a shipped `PreToolUse` handler adapts Bash and `apply_patch` payloads to `read-only-lock.ts`; Bash uses the shared command decision and `apply_patch` reaches its tool-name refusal. The runner registers it on start and resume, obtains Codex's normalized key/hash through `hooks/list`, grants that exact trust with `config/batchWrite`, verifies it before turn 1 and fails closed on any gap. A blocked hook's shared reason is persisted as a v1 `note`. Codex 0.155.1 does not discover request-body hooks alone, so the identical generic handler is also idempotently installed in the active profile's user `hooks.json`; it is inert without xezar's process-local allowlist. The worktree and branch remain writable through other non-shell tools, and MCP tools stay under #324 scoping); Qwen Code **ENFORCED + command-locked** (`--exclude-tools` removes the file writers and the raw executor, only the allowed tools ride `--allowed-tools`, and a run-private `PreToolUse` hook refuses a file writer by name and sends `run_shell_command` through `read-only-lock.ts`). The shared lock refuses every word the shell would still expand, applies checked argument rows through one program-keyed dispatcher, never permits `sed` or `awk`, and otherwise accepts one simple prefix-matched command; its sole compound exception is the exact two-part `printf … | bash <script>` pipe. The readings follow the shell, not the OS (#963): a POSIX shell (Claude Code everywhere, Git Bash included; every backend on Linux/macOS) gets that one reading unchanged, while Codex on win32 runs commands through PowerShell, so its adapter passes `shell: 'powershell'` and a command must also pass a PowerShell reading (backslash literal; unquoted `,` `@` `^` `%`, smart quotes, operators and a literal `"` inside a word refused). On win32 only, a program name also splits on `\`, drops `.exe`/`.cmd`/`.bat` and ignores case, so `GIT.EXE` meets the `git` rows. Plain `Bash` on a read-only step can still write through allowed commands; a `bashAllowlist` narrows it on all three backends, with the shared parser applying on Codex and Qwen Code. A Codex run gets only the MCP servers the project's own `.codex/config.toml` declares, with the project's settings only: the runner asks the app-server (`config/read` with `includeLayers: true`) and switches off home-config servers, plugins, apps and xezar's bridge per thread, failing closed when it cannot ask (#324, `codex-run-isolation.ts`). A project server the home config also names runs on the project layer's own definition; Codex MERGES a per-thread override key by key and has no unset, so any home key that definition does not replace (an `env` entry, a `url`, …) keeps the server off, with the key paths — never the values — in the run's note (#1007). A server whose start fails (`mcpServer/startupStatus/updated` with `failed`, for this run's thread) is named with Codex's reason in a run note (#1026); before, the model simply had no tools and the log said nothing. A server that reports `ready` on this run's thread gets one note per server with its tool count (#1057): the status carries no tools, so the count comes from one bounded `mcpServerStatus/list` (5 s, at most 5 pages), and any failure there drops only the count, never the note or the run. A run with no ready note therefore means the server never reported ready, not that the model never looked its tools up. Runners start their CLI through `platform/process-launch.ts` and stop it through `stopChildTree` (`platform/process-tree.ts`); the rules are in `packages/xezar/src/AGENTS.md` § Processes.
