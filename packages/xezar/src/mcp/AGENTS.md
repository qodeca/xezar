# Guidance for `packages/xezar/src/mcp/`

These rules are the full task-routing guidance moved from the repository root. Root `AGENTS.md` retains the routing index and canonical cross-repository rules.

## MCP server (`xezar mcp` bridge, the tools a project leader calls)

The reference's tables and `mcp-api.json` are regenerated from the real registry by `mcp-api-doc.test.ts`; a tool change without `npm test -- packages/xezar/src/mcp/mcp-api-doc.test.ts -u` fails the suite, and a new tool action needs its inventory records in `tools/api-coverage.testkit.ts`. **A project leader uses these tools only – never the cockpit UI or `/api/v1`** (owner rule, 2026-09-15, #439). It is attached so events are pushed (`<channel source="xezar">` for Claude Code, a started turn for Codex, OpenCode and pi); `leader_events` read is the fallback for a leader that is not attached. Attaching is an MCP action too (#450): `leader_events` `attach` / `stop` / `status` act for the calling session only, with the client derived from that session and never taken from an argument; an OpenCode leader is attached by a person in Settings → MCP connection → Attach leader. GitHub facts (labels, verdicts, merge state) come from `gh`, which the MCP does not carry. Leader-facing text that sends a leader to the cockpit or HTTP is a bug; `leader-mcp-only.test.ts` pins the runtime strings. **A Claude Code leader only receives pushed events when launched with `claude --dangerously-load-development-channels server:xezar`** — without that flag it must read with `leader_events` `read` instead. Per-client leader setup and launch (Claude Code, Codex, pi, OpenCode) is documented once, for the end user, in `docs/guide/13-mcp-leader.md`; do not restate those steps here.
