# Guidance for `packages/xezar/src/`

These rules are the full task-routing guidance moved from the repository root. Root `AGENTS.md` retains the routing index and canonical cross-repository rules.

## CLI entry, `serve`/`run`/`init` subcommands, flags

Uses `node:util` `parseArgs`, no CLI framework. `serve` is the default command. Headless `run` treats `review` as a terminal success status (exit 0). `init` never overwrites existing files. `ensureDataGitignore` writes one blanket `*` into `.local/.gitignore`, so git needs no ignore entry for a new state file under `.local/` — but that tells you nothing about who else reads the directory. At least one external consumer checks the files at the TOP LEVEL of `.local/xezar/` against the names the engine writes today (`runs.json`, `audit.ndjson` and the rest), and fails a gate in every project that uses it when an unexpected name appears. Those names are a shape to match, not a set to enumerate: on a healthy project with no feature turned on, any of them may also appear with a `.lock` suffix, a `.lock.takeover` suffix (the guard every lock release takes, e.g. `audit.ndjson.lock.takeover`), a `.tmp` or `.<pid>.<hex>.tmp` suffix (an atomic write in flight) or a rotation number `.1`–`.4` (`audit.ndjson`), so a check against exact names fails at random. By that consumer's own report, a new subdirectory is safe and a new top-level FILE is a break. We have made no promise about this layout, but a consumer depends on it: put new state in a subdirectory, and announce any new top-level file in the changelog.

## Git / worktree logic

Default for a git task: one worktree at `.local/xezar/worktrees/<runId>`, branch `xez/<id8>` off the configured base branch. `worktree: false` runs in the repo working tree under the repository-root lease, a non-git directory runs in place, and a git task whose requested worktree cannot be created fails closed (`run.ts` marks it `failed` before any step runs). Helpers never throw (except `createWorktree`) — degradation is the caller's policy. Diffs are capped (`DIFF_CAP`). Orphaned worktrees are pruned at startup. **"Which ref anchors *this task's* diff" lives in exactly one place** — `resolveTaskDiffBase` (`git-diff-base.ts`): the merge-base against the **freshest** base ref (`origin/<base>` when the local branch is behind it — agents fetch, they never pull, and a stale local `main` is what turned an eight-line fix into `+59514 −12160`), and, when the agent checked another branch out into the worktree, that branch **as the run found it** (`<branch>@{<run start>}`), whichever of the two attributes fewer changed lines. Attributing a checked-out branch's history to this task is what produced five-figure numbers on review and QA runs (pre-rename issue 591 fixed the Changes tab, pre-rename issue 751 the stored `diffStat`); anchoring those runs at `HEAD` instead then reported `+0 −0` for work they really did commit. A new task-diff surface resolves through that helper and passes the run's `branch` **and** `startedAt`; `worktreeDiff`/`worktreeDiffStat` deliberately keep the whole-branch anchor and each carry a comment saying why.

## Skills (Markdown playbooks, team repos)

A skill is a `.md` file with optional YAML frontmatter (`name`, `description`); its body becomes the agent's extra system prompt. Discovery precedence is local-first: `.xezar/skills` → `.ai/skills` → `.agents/skills` + agent mirrors → global → team repo. Missing dirs are fine; the catalog READ never blocks on the network (background cache in `~/.cache/xez/`, or `<project>/.local/xezar/cache/` in single-project mode — resolve it through `xezCacheDir()`, never `homedir()`). Exactly one caller waits, and only on a miss: a run that NAMES a skill the catalog does not have yet awaits the first fetch already in flight for at most `FIRST_TEAM_CATALOG_WAIT_MS` (20 s, `skills.ts`) and then resolves against it — a fresh project's first task used to run the plain prompt while that fetch succeeded seconds later (#777). It is the same background load, never a second network path; a dry run passes a zero bound; and every fall-through says which of "the catalog was not ready", "no source could be read" and "no such skill" it is, because one sentence for all three is what hid the bug. **That wait's timer is REF'D and must stay so** (#793): the background clone and its pipes are unref'd (#249), and a headless `xezar run` holds no other handle before the agent spawns, so an unref'd timer let node empty its loop and exit 0 mid-step — a success status for a run whose agent never started, with the record left `running`. #249's "exit at once" is about a command that FINISHED its work; here the await IS the work. The `finally` clears the timer, so the loop is held for the wait and not a tick longer, and the wait ends early when the run is cancelled.

## Platform layer (`platform/`)

Where a path, a file replacement, a program search or a process start or stop differs between Windows and Linux/macOS, the answer lives in `packages/xezar/src/platform/` (#963), never in a fresh `process.platform` test at a call site. **Absolute paths:** `isAbsolutePath` for stored values and Git output (lenient), `isFullyQualifiedPath` for a folder a person typed (Windows also refuses `\x`, `/x`, a UNC path without a share and device paths). `posix-literal-scan.test.ts` fails on a new `.startsWith('/')` absolute test or a runtime `/tmp` literal. **Identity:** `path-identity.ts` (`samePath`, `isInsideByIdentity`, `containsPathSegments`, `lookupSamePath`, `isInsideDotGit`) answers "same project / same folder" and is case-insensitive on Windows only; it may WIDEN a refusal and must never GRANT access, so a containment guard never relies on it to let a path through. **Writes:** new and migrated write-then-rename sites go through `writeFileAtomic` / `writeFileAtomicSync` (or `renameReplacing*`): one rename on Linux/macOS with the original error, a bounded retry (about a second) and read-only clearing on Windows only, and the temp removed on failure. One deliberate exception: `agent-config/files.ts` keeps its plain `rename`, because it re-checks containment right before the rename and a retry would widen that check-to-use window. Not migrated yet (deferred, still a plain rename): the MCP writers (`mcp/connection-file.ts`, `mcp/event-controller.ts`, `mcp/event-journal.ts`, `mcp/operation-receipts.ts`, `mcp/reconnect.ts`, `mcp/audit-trail.ts`, `packages/xezar/scripts/pi-leader-extension.ts`) and `server-install/state.ts`. **Program search:** `exe-search.ts` stays the FIRST import of `src/index.ts`, so Windows never runs a program found in a child's working folder. **Rules for the folder:** `platform/` imports only `node:*` and its own siblings; each POSIX branch is byte-for-byte the expression it replaced; every Windows branch is tested on every OS through the trailing `platform` parameter of the pure helpers, and domain functions keep their signatures and follow the host – their call-site tests run the Windows branch on every OS with `withPlatform` (`packages/xezar/test/helpers/platform.ts`), storing the other spelling rather than expecting it on disk; where a Windows syntax rule would reject a POSIX host's path first, force only the identity rule (`platform/identity-platform.testkit.ts`).

**Processes.** Every program starts through `platform/process-launch.ts` (`launch`, `launchFile`, `launchFileAsync`, `launchFileSync`, `launchDetached`, `launchCmd`) and every child stops through `platform/process-tree.ts` (`stopChildTree`, `signalProcessGroup`, `stopProcessGroup`). On Linux and macOS a launch wrapper calls the matching `node:child_process` function with the very `file`, `args` and `options` references it was given – a test pins them with `toBe` – and a stop sends exactly the signal its call site sent before. On Windows a launch never finds a program through the working folder or a relative PATH entry, runs an explicit `.js`/`.mjs`/`.cjs` path through Node, unwraps npm's command shims (and `npm.cmd`/`npx.cmd`) so no cmd.exe runs, sends every other `.cmd`/`.bat` through the strict rule of `batch-line.ts`, and hides the console only for background work (`launchFile*`, `{ hide: true }`), never for an agent session, a check step or the gate lease's command. A refusal is a synchronous `CommandRefusedError` (`XEZ_CMD_*`, `XEZ_SHELL_REFUSED` – error codes, not environment variables) whose message names the file and the argument's position, never its value; a truthy `shell` or a caller's `windowsVerbatimArguments` is refused on every OS. **cmd.exe starts only through `launchCmd`**, which checks every token; `resolveCommand` refuses any other route to it (`XEZ_CMD_DIRECT`). A Windows stop kills the child through its handle at once, then ONE PowerShell (`platform/table-then-kill.ts`, above-normal priority, so a busy machine does not starve it) reads the process table and kills the child's creation-filtered descendants by start time – never `taskkill /T`, which follows stale parent pids. **Process groups** (`detached: true`, `kill(-pid)`) are only for short, bounded probes: the agent quota checker (#892) and the provider sign-in check (#894, a group on POSIX only, through `ownProcessGroup`). Sessions, check steps and every other child stay in xezar's group, because a group loses the terminal's Ctrl+C. **Shutdown:** Windows has no SIGTERM a handler can catch – a kill from another process ends xezar on the spot, with no cleanup – so `serve` stops only from its console. `shutdownSignals` adds SIGBREAK (Ctrl+Break) and SIGHUP (the window closing, which leaves about 5 seconds – 5000 ms by default) to SIGINT and SIGTERM, and `exitAfterStoppingTrees` first holds every `RunManager` (`holdForExit`: no further run-state writes, no new spawn), then stops the tracked trees for at most 8 s (measured 4-6.7 s on a fully loaded machine; closing the window leaves only about 5, so on a busy machine it can end xezar before every started program is stopped; Ctrl+C or Ctrl+Break waits for the full cleanup) while the rest of the shutdown runs, so running tasks resume on the next start as they do on POSIX. The gate lease forwards the same signals to its command through `stopChildTree`. On Linux and macOS the exit stays immediate: stopping what `serve`'s children started at shutdown is Windows-only, and #881 stays open there. **The guard:** `process-spawn-scan.test.ts` fails on a `child_process` reference outside `platform/` (a type-only import excepted), a raw `.kill(` outside `platform/` (the liveness probe `process.kill(pid, 0)` excepted), a `shell` option that is not literally `false`, and an import inside `platform/` other than `node:*` or a sibling. Its only allowances are `server/wsl.ts` (WSL only) and `server-install/steps.ts` (Linux only), one `child-process-ref` each, counted in both directions; route a new call through the layer instead of adding an allowance.

## Run process sweep (`runs/run-process-sweeper.ts`, #943)

When xezar pauses a run for its memory limit, cancels it, or a step hits its time limit, `RunManager` hands the run to its `RunProcessSweeper`, which stops what the run started and leaves one `note` naming it (command lines redacted in full, then cut to 200 characters). **Proof is only xezar's own:** on Linux the exact `XEZ_TASK_ID=<runId>` entry in `/proc/<pid>/environ`; on Windows and macOS the run's ledger, recorded from the sampler's process tables (`onProcessTable`) with the root pinned by start time. Never a name, working folder, command line, port or temp folder, and never for authorization: it is best-effort cleanup, not a containment boundary (macOS misses a process that detaches and loses its parent between two reads). A pid is signalled only while its start time still matches. Programs xezar opens for the user (`launchDetached`, `launchCmd`: an editor, a terminal, a browser) never carry `XEZ_TASK_ID`, so they are never attributed to a run. A run that ends on its own is never swept. Sweeps are enrolled through `trackRun`, one per run at a time, capped at 10 s; a Continue or a fresh body waits for a pending one, for at most that cap, before it starts anything – a pass still running past the cap goes on as best effort and stays identity-checked. A Windows or macOS sweep is skipped outright when the run's ledger is empty, since each Windows pass can start a few short PowerShell runs. Check steps keep today's environment (no `XEZ_TASK_ID`), so their detached leftovers are out of reach until the kit changes.
