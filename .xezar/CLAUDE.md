# Working with the Xezar project kit

This is the maintained project operating kit for developing Xezar with Xezar. Read the repository's `AGENTS.md`, `SDLC.md`, `CODE_REVIEW.md` and `BACKWARD_COMPATIBILITY.md` first; this guide explains the local kit and does not replace those contracts. It does not implement a built-in leader or the distributed kit. The MCP server exists, and a project leader drives this kit only through it (see § Identity, decisions, evidence and recovery).

## Structure

- `config.json`: optional project choices (main base, skill-owned handoff, shared task instructions). No credentials, private accounts, foreign model pins or global resource limits. That last rule is kit policy, not a statement about the engine, and `checks/catalog-check.mjs` enforces it: `maxParallel` is refused because the scheduler genuinely ignores a per-repo value, while `memoryLimitMb` IS honoured per repo and is refused anyway — a memory ceiling is a property of a machine, and this file travels to every checkout. Set either in `~/.xezar/config.json`. Defaults/discovery remain usable without authored config.
- `workflows/`: 18 role workflows. Ten development workflows (`design` included) retain preflight → setup → author → readiness → gates → evidence → handoff, with at most two gate-repair returns. Integration and root synchronization are separate roles. `design-review` and `qa` are read-only like `code-review` (kit → preflight `--allow-root` → one agent step, no readiness, so `branch.owned-by-run` never applies to a detached-HEAD verdict run, #356). `research` is read-only like `business-analysis` (kit → preflight → one agent step, no install, no gates) and is the one workflow granted `WebSearch`/`WebFetch`. The final step stays an agent for interactive questions.
- `skills/`: 20 `xezar-*` roles: triage, issue filing (`xezar-issue-create`, a thin wrapper over the shared `xez-issue-create` procedure at its pinned revision; it is named by no workflow and runs on the built-in `quick-task`), business analysis, external research, planning, UX design (one skill with an authoring and a review mode, run by `design` and `design-review`), implementation, bug investigation, code review, independent QA (posts a `## QA` PR comment and the SDLC QA-gate labels; never runs on the task's own branch), review response, testing, docs, dependencies, release preparation, release changelog, release publish, quality gates, handoff and integration. The selected backend/model is inherited rather than pinned to another vendor.
- `checks/`: executable isolation/setup/Git, gates (`repo-gates.sh`, `repository-checks.sh`), evidence verification (`verify-evidence.sh`), changelog structure (`changelog-check.sh`), resume, integration, root-sync and merge-recovery guards. `checks/lib/` holds shared identity/fingerprints, record/manifest/intent verification, gate lane scheduling and result aggregation, bootstrap and SDLC policy helpers. `infra-tests.sh` exercises isolated synthetic repositories; `xezar-contract.test.mjs` checks real loaders, npm gates, snapshots and local guidance.
- `docs/`: operating instructions (`ui-operations`), worktree and setup discipline (`worktrees`), analysis checklist (`business-analysis`), coordination (`parallel-tasks`), recovery and integration (`recovery`), qualification and adaptation record (`installation`), close-out, improvement candidates (`enhancement-ideas`) and learning from actual development tasks (`dogfooding`). See `docs/README.md` and `docs/installation.md`.
- `pipeline/`: `config.json` (base branch, validation commands, labels, QA gate) and `trackers/github.md`. `checks/xezar-contract.test.mjs` requires the kit's gate list to equal `validation.commands`; the optional `xez-*` team collection reads the rest. Fingerprinted by `checks/lib/common.sh`, but not in the `checks/bootstrap.sh` copy list: a task worktree receives `pipeline/` through Git only.
- `kit-manifest.json`: a frozen 2026-09-09 provenance snapshot of the source baseline, not the current inventory. Listed files may have moved or disappeared, later kit files are absent, and historical hashes need not match current content. Copied into task worktrees and fingerprinted; nothing verifies its hashes. Preserve those historical hashes.
- `.gitignore`: only real local/runtime paths. Maintained documents, workflow/skill definitions and helper scripts are versionable by default, including future ordinary files.

Local-only state includes runs/indexes, worktrees, tmp/cache, UI state, todos, automations/receipts, launch key, credentials, evidence and snapshot markers. Never commit it or copy it into another checkout. Durable task evidence belongs in primary `.local/xezar-tasks/<runId>/`, not reclaimable worktree-local scratch. Do not delete this entire directory to clean runtime; it also contains the maintained kit.

## Discovery and fresh worktrees

The existing Xezar loaders discover `.xezar/workflows` and `.xezar/skills` directly, and the kit is committed, so a task worktree normally receives it through Git. Every workflow still begins with the explicit `kit` command, which locates the same repository's primary checkout and runs `checks/bootstrap.sh`. It copies only maintained kit assets into the validated task worktree, no dirty application source, runtime, personal configuration or secrets. `.local/xezar-kit/snapshot.json` records the local snapshot and is ignored. Existing snapshots are reused on continuation; conflicting existing task content and symlinks are refused, never overwritten — including when the committed kit is already present through Git.

Standalone skills explain the equivalent prerequisite when checks are absent. Bootstrap is a project command, not an engine feature; the current engine's personal-agent-config seeding does not seed this whole kit. Never solve missing files by committing unrelated primary-checkout work or by operating on a peer worktree. Read effective config/tool availability from the current run; successful static loading is not a live-client certification.

## Commands and stage ownership

```sh
node .xezar/checks/catalog-check.mjs
bash .xezar/checks/infra-tests.sh
npm test -- packages/xezar/src/tracked-files.test.ts
bash .xezar/checks/worktree-preflight.sh
bash .xezar/checks/worktree-setup.sh
bash .xezar/checks/repo-gates.sh --fast
bash .xezar/checks/worktree-preflight.sh --record-gate-evidence
bash .xezar/checks/worktree-preflight.sh --verify-gate-evidence
bash .xezar/checks/resume-complete.sh --dry-run
```

Writing commands require the correct Xezar task checkout. Read-only evidence initialization is `worktree-setup.sh --readonly-init`; it installs nothing. Full setup needs Node >=20 and npm, and uses `npm ci`. Dependency freshness includes lock/shrinkwrap, root/workspace manifests, npm config, patches and Node/npm versions. No `.env` auto-loading or secret copying.

The canonical gate list, its reporting order and its lane schedule are in AGENTS.md § Validation. UI smoke/manual QA is separate per SDLC and is not a pass when unavailable. Its maintained browser guide is the repository's `docs/testing/agent-browser.md` (repo root, not `.xezar/docs/`). Never replace real gates with synthetic fixture results or use `npx` to fetch a different test runner.

**Never kill a process by command-line pattern.** `pkill -f <pattern>`, `killall` and `kill $(pgrep -f …)` match every process this user owns anywhere on the machine, not just this task's. Xezar starts each agent CLI with its entire skill text as one `--append-system-prompt` argument, so any pattern that appears in a skill — `repo-gates.sh --fast` is the proven one, it is in all 20 — is present in the command line of every peer agent running that skill. `pkill` then SIGTERMs all of them and spares only the caller and its ancestors, so the task that fired it never sees what it did. Kill your own children with `pkill -P $$`, or save the PID when you start the process and kill that PID. If a pattern is genuinely unavoidable, anchor it to this task's own worktree path and inspect the match list first with `pgrep -fl <pattern>`, which matches identically and signals nothing. A run whose CLI dies on a signal xezar did not send names that signal in its error message rather than reporting a bare exit code.

Complete code, tests, docs, generated outputs and release metadata in development; run focused checks there. Work that is UI in scope (SDLC.md § The design gate defines it) is not done until it carries `design-approved` with the `## Design review` evidence, or `skip-design` with a written reason – a separate question from the gates and from manual QA: the author's QA answers whether it works, not whether it is the right design for the job the surface exists for, and the author is the worst-placed reader to judge that. Gate stage runs the full canonical list. Handoff changes no content and makes no late commit: missing work returns to development/gates. Use `worktree-git.sh` for bound commit/push. Quality-gates repairs the same failure at most twice; workflow repair returns are separately capped at two. Retain failed attempts across reassignment; do not invent a global retry allowance or weaken a control.

## Identity, decisions, evidence and recovery

Validate actual task directory, Git registration, branch `xez/<first8>` and current CWD. Never silently fall back to root, adopt another branch or infer authority from a file. The leader owns goals/plans and review adjudication; specialists provide technical evidence. The project leader works through the Xezar MCP tools only – no cockpit UI, no HTTP API – and is attached so that events are pushed to it as `<channel source="xezar">` messages (a started turn for Codex, OpenCode and pi). `leader_events` pull is the fallback for a leader that is not attached, not the normal path. `gh` stays the way to read GitHub facts (labels, verdicts, merge state) because the MCP does not carry them. Attaching is an MCP action too (#450): the leader calls `leader_events` action `attach` with a new `operationId`, and xezar takes the client from its own session (Claude Code, Codex or pi), so the leader names nothing; `leader_events` action `status` says whether it is attached and can receive pushes. An OpenCode leader is attached by a person in Settings → MCP connection → Attach leader (owner rule, 2026-09-15, #439). A Claude Code leader only receives those pushes when launched with `claude --dangerously-load-development-channels server:xezar`; without that flag, or when Codex is not yet running on the shared local app-server, pi is not yet running xezar's leader extension, or OpenCode has not yet been attached by a person in Settings → MCP connection, read with `leader_events` `read` instead. Per-client leader launch and setup (Claude Code, Codex, pi, OpenCode) is documented once, for the end user, in `docs/guide/13-mcp-leader.md` — this kit never restates those steps, only what a contributor running this kit's tasks as a leader needs on top of it. A mutating tool call that lost a race (another writer changed the task first) answers `stale_version` instead of applying (for example `execution_control`'s `answer_question`/`continue`/`send_message`): re-read the task with `task_read` for its current `version` and decide again, rather than retrying the same stale write. The task version tracks a persisted, monotonic decision revision: status, archive/pin flags, title/title origin, auto-resume, task brief, queued messages, step identity/status, branch and workflow. Participant input advances it too. Transcript/tool/usage progress alone does not change it. This applies to every execution_control action and every other run-version guard; reversing a decision still invalidates an older token. On stale_version, re-read task_read and make a new decision with a new operationId; never blindly retry currentVersion. After a context compaction the leader recovers by reading, never by waiting (#460 § 4): call `leader_events` with action `read` and no cursor before relying on prior pushes, page with `nextCursor` while `hasMore` is true, deduplicate by `eventId`, reconcile current task state, then acknowledge only the events accounted for — a transport receipt is not an acknowledgement. Delivery is at-least-once within retained durable state, not exactly-once: the journal retains at least the newest 10 000 rows and evicts none younger than 14 days, a page carries at most 100 rows or 40 000 bytes, and anything outside that is an explicit gap whose current state is reconciled before `resumeCursor` is acknowledged. Acknowledgement is cumulative, monotonic and idempotent, only `ack` advances it, and no timer re-pushes a row already delivered. Do not poll while idle. Within existing authority proceed; ask genuinely missing decisions with structured options/custom answer. Silence is not approval. An unresolved dependent decision records `BLOCKED`, and readiness must stop before gates. Independent work continues.

Evidence records complete hashed logs, ordered attempts, real outcomes, current content/revision and safe environment facts. Historical validity, reuse here and current eligibility are distinct. New failure cannot be hidden behind an older green attempt; missing logs, skipped/unavailable gates, unknown schemas or changed content never imply pass. Current fingerprint includes local kit content even when a task snapshot is ignored. Cross-task audit is read-only with trusted path containment; CI observations append without rewriting seals.

Consume the current checkpoint and late steering before resume/handoff. A diagnostic-only resume writes nothing; normal resume checks remaining work and eligibility rather than replaying everything. Merge recovery requires matching intent recorded before the authorized operation, preserves partial work and never performs automatic abort/reset. Normal readiness/quality still applies afterward.

Integration uses the exact reviewed head/base, real hosting policy plus SDLC labels/QA, and the actual Xezar CI check. Xezar merges by squash into main: verify resulting content/commit and single-parent/base relationship, then target CI and remaining business scope. Root-sync is a separate Worktree OFF operation, fixed-target fast-forward on a clean expected branch under actual engine root ownership. The guard's authority record cannot prove a live lease. Release publication remains the existing manually dispatched Release workflow when authorized; ordinary CI does not publish.

The `release` role runs one whole patch/minor/major release as one Worktree ON task from a one-line brief (`bump: patch`, optionally `version:` and `dry-run: true`), with no hand-written changelog brief: the `changelog` step derives the `# <version> (<date>)` section from the PRs merged since the last `v*` tag, folds every `# Unreleased` section into it (`checks/changelog-check.sh` refuses more than one or a misplaced one) and commits; the normal readiness → gates → evidence spine follows; and the last step merges the changelog PR, dispatches the Release workflow once for that bump, verifies npm/tag/GitHub Release and merges the bot's bump PR. Every wait on CI, npm or a merge lives in that last step because a non-final agent step that does not set its own `timeout` still falls through to the runner's 30-minute default. Nine author workflows set a two-hour timeout; the release author retains the default. A job timeout does not bound an environment-approval wait: the release skill's finite observation deadline and checkpoint do. Being last also keeps `XEZ:ASK` live for each stop. The MCP mutation gate is not part of this role: `npm run test:mutation:mcp` (`thresholds.break` 80) runs nightly against `main` in `.github/workflows/mutation.yml` (#377) and never in the release path (history: CHANGELOG.md 0.14.0). The role never touches the primary checkout; bringing it to the bump merge commit is the separate `root-sync` role. `release-prep` stays as the brief-driven fallback.

Provenance and the current qualification status — which parts are adapted, fixture-tested, real-task verified, and which remain unqualified — live in `.xezar/docs/installation.md`, which is where they are kept up to date. Existing product requirements in the repository's `docs/features/` remain requirements, not capabilities installed by this kit.
