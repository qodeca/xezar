### 2026-09-20 — Reviewer proposals are options, and the cheaper one was also the truer one (#732)

- The brief handed me two reviewer proposals per finding and told me to pick the one I could prove.
  For Minor A that mattered: restricting the fall-back branch to a real refusal would have REMOVED
  a recovery path (a resumed turn that ends silently would simply fail the step), which is a
  behaviour change nobody accepted. Re-wording the note changes one sentence and nothing else.
  Picking the proposal a red proof can cover, rather than the one listed first, is the rule worth
  keeping.
- Minor B's two proposals collapsed into one fix. Bounding the fall-back by the remaining wall
  clock ALSO made `progress.deadlineAt` honest, because `startedAt + effectiveTimeoutMs` is
  exactly when the one budget runs out once the second execution can no longer run past it. The
  second half of the finding needed no code of its own — worth checking for before writing two
  fixes.
- The "never `git stash`" rule has a cheaper substitute than a scratch copy: write the tests
  FIRST and run them against the untouched file. Six assertions red, then the fix, then green,
  with no file ever moved. The scratch copy was only needed for the compile-time proof, where
  what had to be temporarily broken was a different file (`RUNNER_IDS`) from the one under test.
- The compile-time proof needed its own control. Adding a fifth runner id makes the fixed
  `Record<RunnerId, boolean>` maps error — but that alone does not show the OLD shape was
  fail-open. Putting the pre-fix `readonly RunnerId[]` declarations in a scratch file beside them
  for the same `tsc` run did: two errors on the new shape, silence on the old one, in one output.
- A brief's label can name something the tracker does not have. `gh issue create --label docs`
  failed three times ("'docs' not found"); the repository's label is `documentation`. Reading the
  label list before the third retry would have been faster than retrying.
