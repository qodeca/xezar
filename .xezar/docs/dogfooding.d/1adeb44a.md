### 2026-09-19 — #692 OpenCode goes silent after a rejected permission ask, `bug-fix` step `Reproduce, diagnose and fix`, `xezar-bug-investigation`, Claude (Opus 5) — real-task observed, fixture-tested
- Input: issue #692 with the QA evidence from PR #688 (three reproductions) and the `## QA` comment on issue #686 (a fourth, on a real writing chain at `main` `9e97a149`), the counter-shape run `0f4c4e08` in the primary run store, and the bounded-fix brief asking for either a post-reject silence watchdog in `packages/xezar/src/core/` or a fix to the turn-end seam, with a mandatory red proof. Deliverable: `REJECT_SILENCE_MS` plus the watchdog in `opencode-server-runner.ts`, one mock-server flag, four test cases, `changelog.d/692.md`, a `BACKWARD_COMPATIBILITY.md` entry, this fragment, the phase record and one focused commit.
- Observed: **the issue's two candidate shapes were decidable from the local run store, and the answer was the opposite of the issue's own title.** Scanning all 28 transcripts in `.local/xezar/runs/` that carry a `denied permission` note showed the same shape every time: the denial, the failed tool result, then `turn.completed`/`turn-end` within 0.1–0.3 s. Not one session went silent mid-turn. The #686 QA comment says the same thing in one line — "last event `turn-end` at 12:24:28.958Z" — so the silence is AFTER the turn ends, not instead of it. The runs that "stalled" were therefore sessions that had already gone idle, on a last (interactive) step that correctly parked at `waiting`, driven headless (`xezar run`, which waits only for `done`/`review`/`failed`/`cancelled`) where nobody could answer. Reading the run-history evidence before theorising changed which mechanism got the fix, and it is why the watchdog treats `session.idle` as NOT a sign of life while a new assistant part IS one.
- Observed: **a watchdog that disarms on "any event" would have passed its own test and fixed nothing.** The first design cleared the timer on every SSE frame; against the verified shape that clears on the session's own `session.idle` a tenth of a second after the refusal, so the fix would have been armed for 100 ms and then disarmed forever. The arming predicate had to be the thing the transcripts distinguish — a part the session had not started before — rather than traffic.
- Observed: **naming what the old "wait for the next event" was load-bearing FOR narrowed the change more than any test did.** It carries four things: a slow tool call or model mid-turn, a turn ended with a question a human answers at their own pace, a `XEZ:MONITORING` park, and the run layer's 15-minute idle close. Only the fourth is in the failure's path, and only when the abandoned turn said nothing at all — so the watchdog is armed exclusively after a reject xezar itself issued and disarmed by any new part, which leaves the interactive park (BACKWARD_COMPATIBILITY § 8) intact for every turn that gave the user something to answer.
- Observed: **the 15-minute idle close means the stall was bounded, and that is worse, not better.** A parked last step is closed by `armIdleTimer` after the default 15 minutes; the step then returns `null` and the workflow reports the run as finished. The #686 QA killed its run at 11 m 58 s — three minutes before a close that would have recorded a successful run whose handoff step never opened the PR. The named error this fix raises at five minutes replaces an unexplained success as much as it replaces a wait.
- Regression/control: red proof at `.local/xezar/tasks/1adeb44a-…/red-proofs/red-without-fix.log` — with one line removed (`armRejectWatch` never called) the two stall cases FAIL by timing out at 30 s, while the guard case (a reject followed by a normal event) and the constant assertion PASS unchanged: 2 failed, 2 passed, which is the intended split between the regression proof and the guards. With the fix restored the file is 44/44. The default path is pinned by the suite's own normal-session case, which asserts the exact v1 event counts and the v2 stream.
- Remaining limit: fixture-tested against the bundled mock server only — no live `opencode serve` + DeepSeek session has been run since the change, so the five-minute constant is justified from transcript evidence (healthy gaps of 0.1–0.3 s) and from the surrounding bounds, not from a live reproduction. The watchdog covers a session that says nothing after a refusal; it deliberately does NOT cover a turn that ends after a refusal having said something, nor the headless CLI's own behaviour of waiting indefinitely on a run parked at `waiting` (a separate seam in `index.ts`, left untouched and named in the PR). For OpenCode this replaces the manual "cancel a silent pi/OpenCode task after 15 minutes" rule in `.xezar/docs/model-routing.md` § 6 for this one failure mode; the rest of that rule, and OpenCode's exclusion from the rotation under § 7, still stand until a live retrial says otherwise.
