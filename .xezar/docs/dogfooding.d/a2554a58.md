### 2026-09-20 — A literal key inventory catches what a derived one cannot

Run `a2554a58`, `bug-fix` workflow, #677 wave 1 (the two settings request schemas move into
`packages/contract`, plus an MCP ↔ route request-parity harness).

- **A parity test built from derived schemas proves nothing about a new key.** The MCP's write
  schema is `setConfigInputSchema.omit({ maxParallel: true })`, so a key added to the contract
  flows into BOTH sides and a key-for-key comparison stays green while nobody has decided whether
  the leader may send it. Writing the accepted keys out as a literal list in the test is what makes
  the addition stop. The same literal list caught a mistake in its own first run — the draft
  claimed `PATCH /projects/:projectId` accepts a `name` key, and the contract has only
  `maxParallel` and `tags`.
- **What a deleted schema copy was load-bearing FOR was not what it was for.** Two things the
  `server.ts` copies carried are invisible to every type-level parity check in the repository: the
  custom `'must be at most 20000 characters'` message on `systemPrompt`, which is the literal wire
  text a cockpit toast renders, and the shape's KEY ORDER, which decides the field order inside a
  multi-issue `{ error }` string (the contract had `resources` and `agentDefaults` the other way
  round). Both were preserved deliberately and each got its own runtime assertion; a types-only
  harness would have shipped both changes silently.
- **The narrowing a spec cannot see until you grep.** The spec asked A3 to compare "the schema the
  MCP accepts" with "the schema the route accepts" for each write action. Only two routes really
  validate with a contract schema (`PUT /config`, after this PR, and `PATCH
  /projects/:projectId`); the workflows, automations and agent-config routes still declare their
  own. Comparing the rest against a contract schema no route reads would have been a false parity
  claim, so those actions are classified with the reason instead — and the test refuses to leave a
  NEW write action unclassified, which is the part that keeps the exclusion honest.
- **Red proofs on `cp` copies, never `git stash`.** The stash stack is shared with every peer
  worktree on this machine. Copying the two files to the run's own evidence directory and restoring
  from there cost nothing and cannot pop somebody else's work.
