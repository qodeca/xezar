### 2026-09-21 — The gate-slot control (#672 G4), `feature-implementation` step `implement`, `xezar-implementation`, Claude Opus 5 — real-task observed
- Input: the leader's accepted G4 brief — a Settings → Resources control for `resources.gateSlots` over the existing `PUT /api/v1/workspace/config` route, with "no new route, no new schema", an empty field clearing the key back to the derived default, and one parity test proving both doors accept the same shape. Deliverable: the control, the contract's `null` spelling behind it, the route's delete branch, eight tests across three suites and four documents.
- Observed: **"no new schema" and "clearing deletes the key" were not both satisfiable as written, and the brief could not know it.** G1 had shipped `gateSlots` deliberately non-nullable, with a comment saying so ("No `null`: there is no 'unlimited' spelling"), and the route had no delete branch — so an emptied field had nothing to send. The resolution was to widen the existing field rather than add a shape (`.nullable()`, plus the `=== null → delete` branch the sibling `agentDefaults.runner` already had), because the `null` G1 refused was an *unlimited* spelling and the `null` G4 needs is a *clear*. Those are different values wearing the same token, and the only reason the reversal is safe is that #672 is unreleased. A brief that says "the key is already there" is worth checking against the key's own comments before trusting it.
- Observed: **a test written by the previous slice of the same issue is the thing a later slice has to edit, and it reads exactly like an out-of-scope test.** `workspace-api.test.ts` listed `{ gateSlots: null }` among the 400s, with a comment explaining why. Under the standing "never repair a test outside this pull request's scope" rule that looks untouchable; it is in fact the most in-scope test there is — same key, same issue, behaviour this change deliberately reverses. The distinction that matters is not "did my diff create this file" but "is this test asserting the behaviour I was asked to change".
- Observed: **a response schema that reports only the EFFECTIVE value costs the control its cleared state.** `workspaceConfigResponseSchema.resources.gateSlots` is a plain `z.number()` on purpose (absent and an explicit 1 behave identically), so after a clear the pane re-reads `1` and cannot render "nothing stored" the way the memory field renders `null`. Harmless here — the two states really are the same behaviour — but it is the reason the field keeps local state and the hint names the default in words instead of the control showing it. A future key where absent and the default differ could not reuse this shape.
- Observed: **one `.nullable()` on a contract field re-rendered a generated document.** `mcp-api-doc.test.ts` failed on two snapshots for a row that changed from `integer` to `integer or null`; `npm test -- packages/xezar/src/mcp/mcp-api-doc.test.ts -u` is the documented fix and belongs in the authoring step for any contract edit, not just an added key. This is the second slice of #672 to meet it (G1–G3 recorded the same thing about an added field).
- Regression/control: both AC proofs were run against scratch copies of the three pre-fix sources (paths and sha256 in this run's evidence dir, `red-proof.txt`). Red without the fix: the route's `null`-clears case (400, not 200), all three cockpit cases (no control in the DOM) and the MCP parity case (`expected number, received null`). **Honest split:** the route-level "out of range is refused" assertion is a green-either-way GUARD, not a red proof — the 1–16 bound shipped with G1 and this change does not touch it; the out-of-range proof that is genuinely red is the cockpit one, whose control did not exist.
- Remaining limit: "takes effect without a restart" is verified by reading the mechanism (`xezar lease gates` calls `loadWorkspaceConfig()` per invocation, in a process the gate script spawns) and by the semaphore assertions, not by watching a real second gate run pick up a changed count live. The design review the `needs-design` label asks for is also outstanding: this run's own checks say the control works, not that a number input is the right shape for a limit whose only safe value is the default.
