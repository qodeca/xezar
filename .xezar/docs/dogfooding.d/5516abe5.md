### 2026-09-19 — #704 the changelog fold's `## ` group scan was not fence-aware, `bug-fix` step `Reproduce, diagnose and fix`, `xezar-bug-investigation`, pi (DeepSeek V4.1 Flash) — real-task observed, fixture-tested
- Input: issue #704 (`bug`, `release-0.17.0`) and the leader's bounded brief — one scan in `.xezar/checks/changelog-fragments.mjs` plus `.xezar/checks/fragments.test.mjs`, a red proof run against a scratch copy of the pre-fix script (never `git stash`), and four named kit checks. Base `main` `63d70332`. Kit-only: `.xezar/checks/` ships in nothing, so no released `xezar --version` exhibits this.
- Observed: **the issue's reproduction was exact on current main, and reproducing it first is what made the fix one line.** `mergeIntoSection` is handed the fence map `inside` (it passes it to `sectionEnd` one line earlier) and then walks the section body with `for (const line of body) { if (line.startsWith('## ')) … }`, so an unindented `## ` line in a fence became a group boundary. Folding the issue's fixture exited 0 and rewrote the section with the fenced `## My Custom Group` hoisted to the bottom and the closing fence stranded above it. The fix is `if (!inside[headingIndex + 1 + i] && line.startsWith('## '))` with the loop carrying its index — because `body` is a slice, `body[i]` is `lines[headingIndex + 1 + i]`, which is the index `inside` is keyed by.
- Observed: **the issue's non-triggering claims held, and one of them is the reason this survived to a filed issue.** An indented fence, and an unindented fence whose `## ` line is indented, both folded with only the fragment bullet added. The scan is anchored at column 0, so the corruption needs a column-0 `## ` line inside a fence — which the real `CHANGELOG.md` has never had (its one fence holds `npm install -g @qodeca/xezar`). The issue itself dropped the review's "the real CHANGELOG.md indents its fenced samples" claim; I confirmed the real fence is unindented and simply holds no heading.
- Observed: **my first "no group was hoisted" assertion was itself fence-blind.** Filtering the re-emitted section for `## ` lines counted the sample line the fix had correctly left inside the fence, so the green run failed on the assertion rather than on the fix. The assertion now removes the fenced block first and then checks the remaining `## ` lines are exactly the role's two — which is what "not hoisted" actually means. A test can reproduce a bug's shape and still encode it.
- Regression/control: the red proof is a `cp` of the pre-fix script plus the new test into a scratch checks directory (`.local/xezar/704-repro/checks-pre/`), run with `node --test --test-name-pattern="#704"`: pre-fix `fail 1` on `the fenced sample must survive intact`, post-fix `pass 1`. The whole file is 29/29 after the fix. The two `#684`/`#685` guard cases (`a changelog with no fence folds to exactly the same bytes as before`, `a section of only house headings folds to the same bytes as before`) pass both ways and are labelled guards — they pin the default path the fix must not change.
- Remaining limit: the fold is proven on fixtures, not by a release run against the real `CHANGELOG.md`. Three sibling scans are deliberately untouched, all outside this brief's bounded scope. The issue names two of them as the same root cause: `separatorIndex` (:178) still does not take the fence map (a `---` inside a fence could be read as the section separator) and `parseFragment`'s `## ` scan (:107) is not fence-aware, though it fails closed on an unknown heading rather than corrupting. The third I found while checking the fix: `foldChangelog`'s existing-section lookup, `lines.findIndex((line) => line.startsWith('# <version> ('))`, is also not fence-aware — a fixture whose `# Unreleased` fence holds the literal line `# 0.16.0 (2026-09-01)` makes the fold treat that fenced line as the section heading and shred the fence, which I reproduced and then left alone. It needs the exact version and date being folded, so it is far less reachable than the group scan was; it is still the same class of defect and deserves its own issue rather than a scope creep here.
