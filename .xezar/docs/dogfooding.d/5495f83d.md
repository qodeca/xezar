Author model Opus 5 answering a Fable 5.1 review; one allowed fix round, six findings.

- **A reversal is not finished until every surface that stated the old rule is changed.** The PR
  made the workspace settings writable and fixed the cockpit hint, but three leader-facing strings
  still said "refused": the tool description, the `action` description and the
  `discover_project` `workspace_limits` row, which a leader reads at session start. Two of them
  were copy; the third was an answer FIELD (`status: 'read-only'`) with two tests pinning it. The
  rule worth keeping: when a decision reverses, grep for the old decision's WORDS, not only for
  the code that enforced it — and expect at least one of the hits to be a value rather than prose.
- **`.strict()` on an outer object says nothing about its nested ones.** `{ resources: { maxParalel: 9 } }`
  was stripped and answered 200/`applied` — a success for a change that never happened — through
  BOTH doors, because both validate with the same contract schema. Fixing it in the MCP tool alone
  would have left the cockpit's own route silently dropping the typo. The fix belonged in
  `packages/contract`, and narrowing a shared schema is a backward-compatibility entry even when
  every current caller is type-checked.
- **A test title is a claim.** "needs an operation key, and repeating one changes nothing twice"
  asserted nothing about repeating: the receipt belongs to the generic MCP door, and the tool's own
  suite calls the tool directly. Two test harnesses in this repo (the tool suite and the A/B parity
  world) both bypass the door, so the claim could only be proven in `composition.test.ts`, over the
  real bridge. Worth knowing before writing a replay assertion: *which harness actually runs the
  door you are asserting about*.
- **"Observed through a second GET" is weaker than it looks.** The hot-apply case read
  `composerDefaults` and `skillsAutoUpdate` back through `/workspace/config` — the echo, not the
  consumer. Breaking each real consumer (the run-mode resolution in `task_create`, the updater's
  `effectiveSkillsAutoUpdate`) reds the new assertions and leaves the GET green, which is exactly
  the gap the reviewer named.
- **Red proofs without `git stash`, cheaply.** `git archive HEAD` into the run's own tmp dir plus
  one `npm ci` gave a scratch copy in about a minute; a small script applied one named break at a
  time and restored from a pristine snapshot between runs. Twelve breaks, each with its targeted
  vitest output kept in the run's evidence directory. Nothing was written into the author checkout
  or the primary checkout, and the shared stash stack was never touched.
- **An independent QA verdict and a code review can disagree about the same line, and both be
  right.** The reviewer measured the hosted-mode behaviour, judged it out of scope for this PR and
  wrote it up as a note; QA reached the same fact, judged it a blocker and filed it. Neither was
  wrong: it was an owner decision, not a technical question, and it came back as "allowed — a
  server admin may change limits remotely". What the round then owed was not code but a RECORD and
  a PIN: a test that asserts the permissive behaviour, so the next person who adds the 409 breaks
  a named test instead of quietly reversing an owner decision. A test that pins an allowance is
  worth as much as one that pins a refusal.
- **A parity finding can point the opposite way from the one you fixed.** The review found that
  both doors dropped a misspelt NESTED key; QA found that the ROUTE alone accepted an unknown
  TOP-LEVEL key the MCP door refused. Same schema, two directions, one fix — but only because the
  fix went into the contract. Fixing either door would have left the other asymmetry standing and
  looked complete from whichever side was being tested.
