### 2026-09-21 — #804 port-memory flake was a port-range edge, not lost output, `bug-fix` step `investigate`, `xezar-bug-investigation`, claude-code (claude-opus-5) — real-task observed
- Input: the leader brief for #804, the failing gate log of run `c03361ad` and PR #782's rebuild of the same file. The brief framed the fix as "read the bound port from a signal that cannot be missed instead of chunked or delayed output".
- Observed: **the brief's framing did not match the evidence.** The helper already waits for the cockpit line OR the child's exit, and parses the port only after both pipes drained, so a delivered line cannot be lost. `first.port === undefined` in ~1 s therefore meant `serve` never printed the line. Twelve concurrent reruns did not reproduce it; reading `listenOnFreePort` did: `serve` only moves UP from a busy port, macOS's ephemeral range ends at 65535 (`sysctl net.inet.ip.portrange.last`), and a sentinel there makes `serve` exit 1 with "no free port". A preload that makes the test process's first `listen(0)` return 65535 reproduced the exact gate failure (`assert.ok(first.port)`, actual `undefined`) on the pre-fix copy every time. Linux's default range ends at 60999, which is why CI never showed it.
- Observed: **the bare `assert.ok(first.port)` introduced by #782 cost the diagnosis.** The gate log carried no exit code and no output, so the cause had to be re-derived from source. Every such assertion now goes through one helper that prints both.
- Remaining limit: the original incident's output was not recorded, so the 65535 edge is the one mechanism reproduced with the identical signature, not a proven identity with that run.
