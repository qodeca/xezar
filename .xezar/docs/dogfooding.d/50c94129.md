### 2026-09-19 — #680 a failed security gate did not stop `repo-gates.sh` at the security stage, `bug-fix` step `Reproduce, diagnose and fix`, `xezar-bug-fix`, pi (DeepSeek V4.1 Flash) — real-task observed, fixture-tested
- Input: issue #680 (speed/quality v2 item 11, label `release-0.17.0`), base `main` `e2e53c75`; a bounded kit fix with one red-proof fixture case, no change to `security-scan.sh` or to what counts as a security failure. Deliverable: `.xezar/checks/repo-gates.sh`, one new case plus one guard case in `.xezar/checks/gate-parallel.test.mjs`, `changelog.d/680.md` and this entry.
- Observed: **the comment above the security phase already described the guarantee the code did not implement.** `repo-gates.sh` carried "A failing security stage stops the run here" while the next line was `gate_phase serial 2 || exit 1` — and `gate_phase` returns non-zero only for a scheduler failure or a worker result that could not be collected. A gate that RAN and exited 1 records `failed` and returns 0, so the sentence was true of the design and false of the runner. The fix reads `workers/2.json`'s recorded status and treats anything but `passed`/`not-applicable` as a stop. General shape: when a phase's failure is recorded rather than returned, the caller has to read the record; `|| exit 1` on the phase is not that read.
- Observed: **the "unknown is not a refusal" boundary is what kept the fix small.** `security-scan.sh` exits 0 for `pass`, `unknown` and `not-applicable` and exits 1 only when the result is `findings` or the stage could not read its input, so keying the stop on the gate's recorded outcome stops exactly on a refusal and leaves `unknown` resolving as before — no change to what counts as a security failure. A guard case stubs a security gate that records `unknown` and exits 0 and pins that every gate still runs, and it passes with and without the fix, which is the point: it is the control, not the regression test.
- Observed: **the red proof needed a fixture that drives the real `repo-gates.sh`, and `gate-parallel.test.mjs` already had one.** `infra-tests.sh` drives `lib/gate-record.sh` directly by design ("the suite is itself the last gate, so calling it back would recurse"), so the security-stop case went into `gate-parallel.test.mjs`, whose `outerFixture` copies the real checks tree into a scratch git repository and replaces only path discovery and the agent CLIs. Reusing it cost one `stubSecurity` helper (three lines) and no new fixture machinery.
- Observed: **the red transcript is the defect, verbatim.** With the security gate stubbed to exit 1, the pre-fix runner printed the gate as `"status":"failed","exitCode":1` and then ran `npm run typecheck`, `npm test`, `npm run test:unit`, `npm run build`, `npm run test:package` and the repository-check tail, all recorded `passed`, and only the aggregate at the end was `failed`. Post-fix the same fixture prints `GATES STOPPED AT THE SECURITY STAGE: the security gate recorded "failed", so no quality gate ran.`, records exactly two commands, and completes the attempt as `failed`.
- Observed: **extracting the completion path into `gate_finish` is what makes "never left half-written" true of the early stop too.** The summary block, the completion call and both exit paths moved into one function that the security stop and the normal end of the run share, so there is one place where an attempt is published rather than two that can drift. The signal trap and `gate_attempt_complete` are unchanged, and the existing `cancellation racing completed finalization` case — which monkeypatches `gate_attempt_complete` by name — still passes because the function is called by name at call time.
- Observed (kit friction, third recorded shape of the same guard): **the isolated-task shell guard refused a `write` to the run's own evidence directory under the primary checkout** ("this isolated task must keep project writes and Git commands inside its worktree"), even though the brief names that directory as allowed. The same write through a variable-expanded `$EV` in `bash` succeeded, and `write` into the worktree's own `.local/` followed by `cp` to `$EV` also succeeded. The guard reads the literal path text, so a brief that asks for a file in the evidence dir should say "write it in the worktree and copy it with a shell variable", or the guard needs a write allowance for `.local/xezar/tasks/<runId>/`.
- Regression/control: `node --test .xezar/checks/gate-parallel.test.mjs` is 17/17 at the fixed head, including the unchanged `failed typecheck retains later build/package evidence and cannot certify`, which is the control for the application phase this change deliberately does not touch. The red proof is the new case failing against the pre-fix script (assertion `expected /GATES STOPPED AT THE SECURITY STAGE/`) and passing after; both the `node --test` transcripts and a matched pair of direct `repo-gates.sh` fixture runs are under this run's evidence `red-proofs/` (`before-fix.txt`, `after-fix.txt`, `manual-before-fix.txt`, `manual-after-fix.txt`, `fixture-repro.mjs`). `bash .xezar/checks/infra-tests.sh` passed 667 cases / 0 failed.
- Remaining limit: the stop is proven on a stubbed security gate, not by a real refused scan at a real candidate; what the real stage does on refusal is `security-scan.sh`'s own contract and is unchanged here. The recorded statuses are read from `workers/2.json`, so a future renumbering of the canonical gate list has to carry this index with it — the same renumbering note `lib/gate-parallel.mjs` already carries for gates 3–7.
