# Worktree and setup discipline

Every writing task owns .local/xezar/worktrees/<runId>, on xez/<first8>. Xezar owns creation/retention. Do not adopt a branch, use a peer checkout, or fall back to root after reclaim. Bootstrap copies only allowlisted maintained kit files after validating primary repository/task/branch; it refuses symlinks and conflicting existing files. It never copies the current root application's dirty changes. Run preflight before every write and on continuation; errors show actual CWD and predicate.

Setup checks Node >=22/npm and npm ci freshness, then writes task context. Freshness covers package-lock.json, npm-shrinkwrap.json, package.json, .npmrc, patches, workspace manifests and Node/npm versions, and requires every workspace package to resolve to the task's own copy: a task worktree sits inside the primary checkout, so a missing `node_modules/<workspace>` link silently loads the primary's source instead (#286). Setup and the gates refuse such a tree; a command run by hand before setup is not guarded, so run setup first. With `dependencies.units` (read from the base branch) setup and the first gate both run `.xezar/checks/deps-restore.sh` instead: each unit is installed in turn (`npm ci`, Yarn 1 with a frozen lockfile, `dotnet restore <entry>`), freshness is a stamp per unit under .local/xezar/cache/deps, bound to the installed tree by a nonce, the folder's inode and a metadata digest of everything inside it (each entry's path, type and inode, a link's target, a file's size, mtime and ctime), so a package folder replaced or a file edited in place is stale. Build caches the gates write directly inside a node_modules (`.cache`, `.vite`, `.vite-temp`, `.vitest`, `.tmp`, `.astro`) are left out only while they hold no package.json, no `.bin` and no link; a link into one, a tree the digest cannot read and a digest slower than `XEZ_DEPS_DIGEST_TIMEOUT_MS` (default 60000) are each not fresh. The limit, plainly: anyone inside the task who can run `deps.mjs stamp` can re-stamp whatever tree is there, so the stamp tells an honest run its install is unchanged and is not a seal against a dishonest one. A single npm root's stamp, `node_modules/.xezar-deps-stamp`, carries the same digest of its node_modules (the stamp itself left out), so the same changes are stale there too; a stamp written before 3.1.0 has no digest and reads as not fresh, so each task installs once. The gates re-stamp once every gate has passed, so what the gates themselves write into node_modules (`prisma generate`'s `.prisma/client`, Vite's `.vite/deps/package.json`: folders holding a package.json, which the build-cache rule cannot leave out) does not make the next `--fast` run or resume reinstall. The re-stamp covers only the tree the same run installed or found fresh, and is skipped, with the reason printed, when a gate failed, the input fingerprint changed, or node_modules was replaced or its stamp rewritten during the run; a skipped re-stamp leaves the old stamp, so the next run installs again. It adds no trust beyond the limit above. A numeric root .nvmrc pins the Node major from an already-installed nvm version. Never copy node_modules or credentials. Read-only initialization makes only evidence context; code execution needs an independently prepared isolated checkout. No fabricated run ID.

Use worktree-git.sh commit/push with current CWD and task identity; it binds named ref and refuses merge-in-progress. Reuse original task/PR for corrections. Missing ownership needs deliberate recorded migration, not an incidental duplicate. Results that must survive retention live under primary .local/xezar/tasks. No archive-before-reclaim mechanism is presumed necessary; preserve non-rebuildable evidence explicitly.

Source snapshots are recorded as .local/xezar/cache/kit/snapshot.json in the ignored task runtime tree. Bootstrap never refreshes an existing task snapshot. A differing tracked asset is kept only when it equals the fork base's blob (`git merge-base HEAD origin/<base>`), which is the primary checkout lagging a merged kit PR; any other differing asset, or no reachable fork base, is refused instead of overwritten: use that revision's own kit or a deliberately reconciled later task, not a hidden update. The one exception to that: every kit step writes a fresh copy of the primary checkout's `.xezar/checks/` to .local/xezar/cache/kit/checks/, the only place a review or QA step runs kit scripts from (D13). Checking a pull request out replaces the tracked `.xezar/checks/` with that pull request's own copies, which may be old, missing or changed; the copy outside the tracked tree keeps the review on the kit it was launched with, and `review-run.sh checkout` refuses a head that tracks a file there. No generic product seeding behavior has been added.
