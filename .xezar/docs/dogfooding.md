# Learn the recommended way of working through real Xezar development

Every future authorized feature/bug/docs task is also an opportunity to assess the workflow, skill and effective settings it actually uses. Do not launch an extra goal merely to fill this ledger. The leader preserves the feature's AC and records concise operational observations alongside its delivery evidence.

Four evidence levels, never conflated: **adapted** (installed and statically checked), **fixture-tested** (named isolated case passed on identified kit bytes), **real-task verified** (observed in an actual authorized task, with runtime/kit/result evidence), **recommended** (reviewed guidance justified by real-task results and known limits). Copying or a green fixture is insufficient for a recommendation.

Record: task/goal and criterion, workflow/skill/effective config, code head/base, runtime/build and kit digest, expected behavior, observed behavior, evidence link, problem/impact, hypothesis/change, regression or control, outcome, remaining limit, owner/next trigger. Keep private logs in primary .local/xezar-tasks; publish only safe conclusions in this maintained guidance. Missing tokens/cost/timing remain unknown.

Loop: observe during real work → classify problem versus environment/unknown → fix the narrow workflow/skill/check/config cause within authority → test the regression and unchanged quality → validate in a later relevant real task → record the bounded recommendation and limits. Do not schedule fixed reviews, weaken gates, fabricate performance benefits or overwrite active snapshots. Recommendations can be revised with rationale and evidence; not every one-off brief needs a permanent skill.

Installation validation is reported in installation.md. Real-task entries follow; each names its evidence level.

### 2026-09-09 — issue #28, single agent step (`quick-task`, no kit workflow) — real-task verified

- Goal: kill the intermittent CI failure of `github.test.tsx › the follow-up prompt template menu (#413) › inserting a second template stacks it below the first`. Code head `5e8b30c` (v0.11.2), branch `xez/ba65de24`, Node 24 / npm 11, macOS.
- Observed: the flake was a **test** defect, not a product one, and not the obvious "asserted too early". The helper used *"the option node unmounted"* as proof that the insert had landed. That proxy is false: `insertPromptTemplate` restores focus to the textarea inside a `requestAnimationFrame`, Radix dismisses an open popover when focus lands outside it, and a frame deferred by a loaded runner therefore closes the **next** menu with nothing selected. The helper read the empty menu as success and returned without ever clicking.
- Evidence: an in-suite probe (menu open, `textarea.focus()`) printed `option present: true` → `false`, so the dismissal is real in jsdom rather than inferred. Reverting the helper body alone, with the new regression test kept, reproduced the CI diff byte for byte.
- Lesson (recommended): in this cockpit's suite, **never wait on a popover/menu disappearing as proof that its action ran.** Closing is a side effect a dismiss layer can produce on its own. Wait on the state the action was supposed to change — here the textarea value — and re-drive the interaction (reopen, re-click) until it does. The same shape applies to every Radix `Popover`/`Command` picker in `packages/web`.
- Observed: the "prove the regression test fails without the fix" rule needs an adaptation when the fix and the test live in the same file — `git stash push -- <file>` removes both. Reverting only the fixed helper body while keeping the new test is the honest equivalent, and it is worth saying so in the PR body rather than claiming a stash proof that was not run.
- Regression/control: the new deterministic case queues `requestAnimationFrame` callbacks, releases them with the menu open, asserts the menu really was dismissed, then requires the pick to land. The whole file passed 30/30 consecutive runs (120 tests each) after the fix; the full canonical gate passed on the committed tree.
- Remaining limit: one macOS machine and jsdom only. The fix removes the test's dependence on the timing, but it was never reproduced on the actual ubuntu-latest runner, so "the CI flake is gone" stays an inference from the mechanism plus 30 local runs, not an observation of CI under load.

### 2026-09-09 — issue #22, single agent step (`quick-task`, no kit workflow) — real-task verified

- Goal: a per-step `timeout` field in the workflow YAML, so a non-final agent step can raise or drop the 30-minute wall clock that killed two earlier bugfix tasks mid-investigate. Delivered as PR #40 on `main` at `5e8b30c` (v0.11.2), commit `81d7f08`.

It forwards its arguments to `git commit` with no `-a` and no `add`, so an unstaged tree produces a clean-looking "no changes added to commit" and exit 0 without committing. `git add -A` first, then the guard. Worth knowing before a workflow's commit step reports success on an empty commit.
- Observed (confirms the #27 entry): the gate ran twice for one commit — once dirty as a development check, once on `81d7f08` for the seal, which `--record-gate-evidence` then accepted and `--verify-gate-evidence` reported as *currently eligible*. - Observed (confirms the #18 entry): the tagged-stash red-proof protocol held with a peer worktree present. Stashing one source file at a time is the useful shape — reverting `run.ts` alone turned 3 of 4 wiring tests red with a real assertion diff, while reverting `types.ts` produced only import errors. An import error is weaker evidence than a diff; prefer the stash that leaves the test loadable.
- Observed: a test written to pin an UNCHANGED default passes both with and without the fix, by design. That is the control, not a failure of the red-proof; say which of the new tests is which when reporting, or a reader counts it as a gap.

No UI smoke, no kit workflow step, and no `.xezar/` workflow was changed to use the field (a separate task).

### 2026-09-10 — concurrent gate runs starving each other (observed during ordinary work, no dedicated task)

- Goal: none — this was observed while several gate runs happened to be in flight at once, and is recorded because `parallel-tasks.md` asks for observed contention to be written down before parallel speedup is claimed.
- Observed: vitest's default worker count is `availableParallelism() - 1`, which is per RUN. Ten concurrent gates on an 18-core machine therefore meant roughly 180 worker processes. The symptom was not a crash and not a failing assertion: unrelated suites timed out at 909s on a single file, and a different 17 files failed on every run. It reads as flakiness, which is why it survived a while.
- Change: a cap in the repository's root `vitest.config.ts` — `min(4, availableParallelism() - 1)` — which holds the fan-out to about 8 of 18 cores at the shipped `maxParallel` of 2, and turns the ten-run worst case into roughly 2.2x oversubscription instead of 10x.
- Regression/control: none, and this is the honest limit of the entry. The cap is reasoned from vitest's own default and the observed symptom; no timed before/after was run. It is also a deliberate NO-OP on CI (a 2-core runner resolves to 1, a 4-core to 3), so a green CI run is not evidence either way, and nothing in any suite pins the cap — removing it is green everywhere. Recorded as a gap in the repository's `docs/testing/coverage-gaps.md`.
- Lesson (recommended): worktrees isolate files, not the host. When scheduling parallel tasks, the shared resource that bites first is CPU, and its symptom is a timeout in a suite that has nothing to do with the change.
- Remaining limit: one macOS machine, one observation. Whether four workers per run is the right number on a smaller or much larger host is unmeasured.

### 2026-09-09 — PR #40 / issue #22, INTEGRATION task (`quick-task`, no kit workflow) — real-task verified

- Goal: rebase, independently review and merge someone else's PR. Reviewer/integrator role, not author. Code head `58fd842` (v0.11.2) → merged as `e437c24`. The first recorded dogfooding task whose deliverable is a merge rather than a diff.
- Observed: **the branch to rebase was checked out in a PEER worktree**, so the brief's `git checkout -B xez/8128ea4b origin/xez/8128ea4b` would have been refused by git — and taking that ref would have been operating on another task's checkout, which `.xezar/CLAUDE.md` forbids. The working shape is to rebase on a THROWAWAY local branch inside your own worktree and push the result to the remote ref: `git checkout -B integrate/pr<n> origin/<branch>`, rebase, then `git push --force-with-lease=<branch>:<old-sha> origin HEAD:<branch>`. Use the explicit `--force-with-lease=<ref>:<sha>` form when pushing to a ref other than the current branch's upstream. The bare `--force-with-lease` does NOT compare against the current branch's upstream — per `git-push(1)` it protects each ref being pushed to using the remote-tracking ref we have FOR THAT REF, verified accepted in a scratch repo on git 2.55.0 while the current branch tracked something else entirely. The real trap is the other half of that rule: when we have no remote-tracking ref for the destination, git expects it to be absent and refuses with `stale info` (also reproduced), and a stale local copy fails the same way. That is exactly the state after fetching a branch this worktree has never tracked, which is the normal case here. The explicit form states the SHA you actually reviewed instead of depending on what your refs happen to know, and it is the only form `git-push(1)` does not mark experimental — so it is the safer habit even when the bare form would have worked.
- Observed: **a rebase silently invalidates the sealed gate evidence**, because the seal is keyed by head SHA and every commit gets a new one. Re-running `repo-gates.sh --fast` on the rebased tree is not optional politeness; the old record is evidence for a commit that no longer exists. `--fast` then declined on its own (node_modules did not match the lockfile in a fresh worktree) and ran `npm ci`, which is the guard working as documented.
- Observed: **a force-push DOES fire the `pull_request` CI event, an ordinary push apparently did not.** The pre-rebase tip `afc65f7` had no run at all while its parent `81d7f08` had one; the rebased head got a run within seconds of the push and no manual `gh workflow run` was needed. So "no checks reported" is a GitHub event that did not fire, and the cheap fix is to move the branch again rather than to dispatch a workflow. Never read it as a pass.
- Observed: proving a rebase changed nothing is one command, and it is worth doing before reviewing a line: `diff <(git diff <old>^ <old>) <(git diff <newbase> <new>)` with `^index ` lines stripped. It answers "is this the same change" in a way that reading the diff twice does not.
- Lesson (recommended): when the QA route says "exercise the flow" and the cockpit's own module is the untested part, **run the shipped module directly** (`TMPDIR=/tmp npx --no-install tsx`) instead of writing a test you will not commit. It is honest evidence of the real code, and it is not a test claiming coverage the repo does not have. Two traps: `tsx` fails with `EINVAL … .pipe` when `TMPDIR` is the long xezar tmp path, and a script outside the repo must import by absolute path.
- Lesson (recommended): a live `XEZ_DRY_RUN=1` cockpit is the fastest QA instrument in this repo. Booting one via `npm run test:e2e` leaves the instance up (`.local/qa/test-env.json` carries the port), so the browser suite and a hand-driven API pass can share one boot. Drive the same endpoints the UI drives — parse, save, reload, `POST /runs` — and every refusal path is one `curl` each. Always `sh scripts/test-env-down.sh` afterwards, and delete anything the save route wrote into `.xezar/workflows/`.
- Observed: `gh pr review --approve` is refused with `Can not approve your own pull request` whenever the authoring task and the reviewing task share the GitHub account, which is always in this setup. The review still has to exist as a durable artifact, so post it with `gh pr comment` and say in the text why it is a comment. `integration-preflight.sh` already understands this — it reported `policy for main requires 0 approving reviews` and named the authority record as the review that matters.
- Regression/control: no source change, so no red-proof applies. The controls run were the full canonical gate on the exact merged head (7/7 pass, 419 infra fixtures), GitHub CI on the same head, `npm run test:e2e` = `TEST_E2E_STATUS=passed` with a real Chrome, and a post-merge tree comparison (`git diff <squash-commit> <reviewed-head>` empty) proving the merged content is what was reviewed.
- Remaining limit: one macOS machine. The Chrome profile was locked by another local session, so the workflow canvas was never clicked through visually — the cockpit code was exercised as a module and over HTTP instead. `--force-with-lease` was never observed being REFUSED, so the "someone else moved the branch" stop path is untested.

### 2026-09-10 — issue #170, single agent step (`quick-task`, no kit workflow) — real-task verified

- Goal: close the last live browser-suite failure blocking PR #128 (`github.e2e.ts:119`, `Element not found: [data-slot="gh-tabs"] …`). Code head `1b82f90` (post-#169), branch `xez/e7473943`, Node 24.20 / npm 11, macOS. Delivered as PR #173.
- Observed: the cause was a **product** bug, not a test one — the bare `/github` index rendered the whole Issues screen while `GET /api/v1/ui-state` was still in flight, then discarded it via `<Navigate/>`. A user with Pull requests remembered sees that flash too. Fixing the product left `github.e2e.ts` byte-identical, which is the better outcome than a spec patch.
- Lesson (recommended): **when a race will not reproduce because the local machine is too fast, do not add load — delay one response.** A ~90-line throwaway proxy in front of the booted `.local/qa` server, delaying only `GET /api/v1/ui-state` by 800ms, turned a 1-in-5-CI-runs failure into 3/3 deterministic. Two traps, both real: the proxy must live in its **own process**, because `AgentBrowser` drives the CLI with `execFileSync` and a same-process proxy can never answer the page it is serving (the symptom is a 60s `goto` ETIMEDOUT); and the census must be captured by a page-side `MutationObserver` + `requestAnimationFrame` recorder, because polling through the CLI is ~20ms per call and the window is one commit. Clicking during the window is not a substitute — a click that SUCCEEDS cancels the redirect it is trying to catch.
- Evidence: the recorder printed the three states in order, unedited — `/github :: gh-row×3, gh-tabs×1, …` → `/github/prs :: (no gh-* slots at all)` → the PRs screen — which is exactly the census #170's comment named as the discriminator. Before that, 15/15 unmodified rounds showed `gh-tabs×1` on every frame with the click succeeding, so the visibility/hit-test alternative was refuted rather than assumed.
- Observed: **the obvious spelling of the fix was wrong twice, and only a request COUNT caught it.** React Query re-enters `status: 'pending'` whenever an errored, data-less query refetches, and `retryOnMount` fires that refetch every time a new observer appears — so `if (index && uiState.isPending)` and `if (index && uiState.isLoading)` both oscillate against a failing ui-state read: 3939 renders and 1649 requests in two seconds, versus 2 without the guard. Neither spelling failed a normal assertion; the test that caught it asserts `sent.filter(…).length < 5`. Worth generalising: **a render guard on a query's transient STATUS is a loop waiting to happen — gate on the monotonic `dataUpdatedAt`/`errorUpdatedAt` instead**, and pin it with a request count, not just a rendered result.
- Observed: `bootstrap.sh` refused with `existing task asset differs: checks/catalog-check.mjs; reconcile deliberately`, because the primary checkout had uncommitted `.xezar/` edits from a peer task (#167). The committed kit was already present in this worktree through git, so the correct reconciliation was to keep it and skip the bootstrap — copying the primary checkout's dirty state would have imported another task's in-flight work. The refusal is the guard working; do not "fix" it by overwriting.
- Observed: **`main`'s CI has no browser-suite job** (it arrives with #128), so a PR against `main` cannot prove a browser fix on a GitHub runner. The working shape is a scratch branch = `origin/<#128 branch>` + the fix commit, `gh workflow run ci.yml --ref <scratch>`, read, then delete the branch. Build it in a throwaway `git worktree` under `/tmp` and remove it — never check the peer branch out here.
- Observed (independent confirmation of Q4 of #170's comment): the first scratch run was named `xez/e7473943-ci-proof` and failed `repo-git.e2e.ts:164` + `settings-agents.e2e.ts:123` while `github.e2e.ts` passed. Re-pushing **the same commit** as `ci-proof-170` passed all 35 files. The precondition for the branchless failure is therefore *"every ref in the checkout is `xez/*`"* — `packages/xezar/src/server/git.ts:103` filters those names out — and not `fetch-depth`. A xezar task branch is the one branch name under which xezar's own e2e suite cannot see a branch.
- Regression/control: the new unit test is red without the fix (`× opening /github renders no tab at all until ui-state answers`, 76ms) and green with it; the second new test is a CONTROL that passes both ways and exists to pin the oscillation hazard. Full canonical gate 7/7 on the committed head, `npm run test:e2e` = `TEST_E2E_STATUS=passed` four consecutive local times, and `TEST_E2E_STATUS=passed` on a GitHub runner (run 34475970071, 308.63s).
- Remaining limit: the real `github.e2e.ts:119` `Element not found` was never reproduced on this machine, so the #169 `click` diagnostic itself never fired here — the census comes from the recorder instead. A ~60-attempt delay sweep (60–280ms) produced zero click failures because the agent-browser CLI waits briefly for a selector on its own; at delay=120ms the click took ~700ms instead of ~25ms, i.e. it waited out the very window this fix closes. That CLI wait is undocumented in `docs/testing/agent-browser.md` and its budget is unmeasured.

### 2026-09-10 — PR #128 / issues #60 + #147, INTEGRATION task (`quick-task`, no kit workflow) — real-task verified

- Goal: review and merge someone else's PR, where the PR itself changes the CI gate that the kit's own merge guard depends on. Reviewer/integrator role. Reviewed head `b768e294` rebased onto `main` at `761c3535` → `50a0fa9d`, merged as `980b542`. Node 24.20 / npm 11.19, macOS, 12 peer worktrees present.
- Observed: **a `pull_request` CI run uses the workflow file from the MERGE ref, not from the branch.** #147 was filed partly on the fear that renaming a CI job leaves a window in which open pull requests still report the old check name. The same-commit rule is right for a different reason (the kit travels with the branch, so an integrator's `PROJECT_CHECKS` and the head's `ci.yml` must agree), but the feared window does not exist: minutes after the merge, the one other open pull request (#174) reported both NEW check names on its own head with nobody touching it, because GitHub resolved `refs/pull/174/merge` against the new base. **A CI-workflow change therefore reaches every open pull request on its next run.** Worth knowing before anyone schedules a rebase sweep after a job rename.
- Observed: **the repository's only enforcement of a CI check NAME is the kit's own `PROJECT_CHECKS`.** `main` carries no branch protection and no rulesets (`GET /repos/…/rules/branches/main` → `[]`, `…/branches/main/protection` → 404). Check that before treating a job rename as dangerous — the answer changes the blast radius completely, and it is two API calls.
- Lesson (recommended): **to prove a CI acceptance criterion that requires a RED run, use a throwaway scratch branch whose name is NOT `xez/*`, dispatch `ci.yml` at it, read the result, delete the branch.** #60's first criterion ("a deliberately broken cockpit assertion covered only by a browser spec fails CI") cannot be shown on the pull request itself without reddening it. The scratch run failed `Cockpit browser e2e` on exactly one spec (`smoke.e2e.ts`, `expected 5 to be 2`, 34/35 still green) while `verify` stayed green — evidence the new job discriminates rather than merely passes. The `xez/*` exclusion is load-bearing and is recorded in the #170 entry above: `packages/xezar/src/server/git.ts:103` filters those names out, so a `workflow_dispatch` checkout whose only branch is `xez/*` fails `repo-git.e2e.ts` and `settings-agents.e2e.ts` for reasons unrelated to the change under test.
- **Remaining hazard, now that the browser suite is a required job:** that same `xez/*` trap does NOT bite ordinary pull-request runs — they are detached at the merge ref, so the branch list is not all-`xez/*` — which is why every run in this task was green. It DOES bite `workflow_dispatch --ref xez/<id8>`, which is the natural way an agent proves a CI fix from its own task branch. Dispatch from a renamed scratch branch instead. Unmeasured: whether any other checkout shape reaches the same all-`xez/*` state.
- Observed: **bringing a task worktree to a reviewed head is a fast-forward, not a rewind.** `git merge --ff-only <rebased-sha>` from a branch that is an ancestor does it with no history rewrite, and the sandbox's own safety hook refuses the destructive spelling anyway. Afterwards `repo-gates.sh --fast` recorded a normal attempt for that SHA and `--record-gate-evidence` sealed it. This confirms the #40 entry from the other direction: a rebase invalidates a seal, but re-gating the rebased tree is one command and the seal then keys to the SHA that is actually merged.
- Lesson (recommended): **a shipped CI shell step can be regression-tested locally, without a runner.** Parsing `ci.yml` with `yaml.safe_load` and writing `jobs.ui-e2e.steps[].run` to a file gives the exact shipped bytes; driving it with a fake `npm` on `PATH` reproduced all three `TEST_E2E_STATUS` outcomes and showed the naive `run: npm run test:e2e` going green on `skipped` where the shipped step goes red. That is a real red-without-the-fix proof for a YAML change, which otherwise has no test surface at all — and it is more honest than re-typing the logic into a harness, because a retyped copy can drift from what shipped.
- Regression/control: no source change by this task, so no red-proof applies to it. The controls run were the full canonical gate on the exact merged head (7/7, 420 infra fixtures, first attempt, sealed digest `541a4ad8…`), `catalog-check.mjs` OK, four consecutive green `Cockpit browser e2e` runs on GitHub runners (35/35 spec files and `TEST_E2E_STATUS=passed` each, including on `main` after the merge), the deliberate-break run above, a post-merge tree comparison (`git diff 980b542 50a0fa9d` empty) and a single-parent check on the squash. The guard's refusal path was exercised too: pointed at a commit with no CI run it refuses on both new names with `checks.absent`.
- Remaining limit: one macOS machine. `SKIP_ALLOWED` was reasoned about but never exercised — no run in this task concluded `skipped`, so the "a check that is not permitted to skip was skipped" refusal stays unobserved here. The 30-minute `ui-e2e` cap was never approached (worst observed job 6 m 41 s), so its behaviour on a genuinely slow or cold-cache runner is unmeasured.
