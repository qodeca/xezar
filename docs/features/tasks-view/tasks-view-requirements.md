# Tasks view — business requirements

Date: 9 September 2026  
Business stakeholder: Marcin Obel  
Status: Ready for team handoff as business requirements. Technical specification, implementation, and validation remain to be completed.

## Purpose and scope

Make task progress and purpose understandable without opening a task to read its complete title or summary. Replace the project Tasks list with five tabs of full cards.

The scope follows the approved architecture condition: a common main view may be updated for both project and aggregate Tasks if that is simpler; separate main views mean only project Tasks changes. The current implementations are separate, so this feature applies only inside one project. The aggregate/global Tasks screen stays unchanged. Shared controls alone do not justify extending the redesign.

It is recorded here rather than edited into the paragraph because the paragraph is the approved business scope and this crossed it. The redesign this document specifies — five tabs of full cards — is still untouched on both screens, so the boundary that matters for THIS feature is intact; what changed is that "the aggregate screen stays unchanged" can no longer be relied on as a background fact when planning it.

All requirements and counts below are scoped to the current project. All means all eligible statuses in that project, not all projects. Archive actions must not affect another project. The requirements and acceptance criteria are normative; the source evidence section describes current implementation only.

### Boundaries

- Preserve existing operations except where an explicit requirement below changes their presentation or eligibility. Preserve review-gate activation, permissions, automatic resumption, and monitoring behavior.
- Do not add an Archive tab, collapsed task-list substitute, account/profile display, extra filters, cross-device synchronization, or a new summary-model selection requirement.
- Tentative backlog ideas without a concrete execution decision are outside Tasks, including Planned and All. Inbox default enablement is a separate feature; no Inbox change or GitHub-to-Inbox integration is included here.
- External-leader MCP integration is outside scope. Concrete leader-planned tasks are included regardless of how their source is implemented.
- Cost omission applies to these cards, not stored measurements or other screens. The comparison screen and winner-selection workflow remain unchanged.

## Tabs, classification, and activity

Use this exact tab order. Every tab uses the same full-card presentation.

| Order | Tab | Eligible task category before search |
| --- | --- | --- |
| 1 | Planned | Concrete work awaiting start conditions: queued tasks, leader plans, dependency waits, and valid scheduled automatic resumption. |
| 2 | Running | Work in progress, including waiting for tests/subtasks without needing a human or leader decision. |
| 3 | Needs attention | Human/leader interaction, review awaiting approval/correction, or unresolved failure requiring a decision. |
| 4 | Finished | Completed work, cancelled tasks, and failures explicitly closed without retry. |
| 5 | All | Individual tasks across these statuses; archived tasks only when Show archived is enabled. |

Archive is a separate flag, not a status: archived tasks are excluded from the four category tabs and from All by default. The status rules do not override that visibility restriction.

On the first visit to a project's Tasks view, select Running. Later visits restore that project's last selected tab. A status update moves the card and updates counters without changing the selected tab or search phrase. All updates the same task rather than creating a copy. Each variant is an individual task card; membership in All and a category is not a duplicate run.

### Classification rules and exceptions

| Situation | Required behavior |
| --- | --- |
| Concrete leader plan without a run/queue entry, waiting for dependencies | Planned. Start automatically once dependencies and start conditions are satisfied. An exact date or existing execution record is not required. |
| `queued` | Planned while waiting for execution. |
| Usage-limit stop with valid scheduled automatic resumption, including a `failed` record with `autoResumeAt` | Planned, with readable resumption time and no work spinner. This exception takes precedence over generic failure classification. Preserve the existing resumption engine. |
| Usage-limit stop without the information needed for automatic resumption | Needs attention; no spinner while stopped. |
| Other unresolved failure requiring retry/closure decision | Needs attention. Stopped execution alone does not make it Finished. |
| `waiting` for a human or leader; `review` awaiting approval/correction | Needs attention; no work spinner after agent work ends. Do not infer permissions or a responder identity from status alone. |
| `running`, including waiting for active tests/subagents without a decision | Running. Show a waiting indication where applicable; spinner reflects actual work of the whole task. |
| `done` | Finished. |
| `cancelled` | Finished, clearly marked Cancelled, without a spinner or implication of success. |
| Failed task explicitly closed without retry | Finished, retaining error/history and indicating closure without a fix, without implying success. |

For unresolved errors, provide **Close without retry** in task details. A human/leader's explicit choice invokes closure. It does not archive, mark read, cancel, or rerun the task, and adds no separate confirmation requirement. It is blocked offline like other task mutations.

### Work indicator and attention information

Show a simple status from task data, with no model analysis. A small spinner represents actual activity across the whole task, including tests or subagents working while the main agent waits. Queuing, a future resume time, monitoring status alone, or missing evidence must not imply active work. Stop the spinner when work stops; the disconnected-state rule below overrides the indicator when current activity cannot be confirmed.

For a task requiring attention, show a short waiting reason and whether a user/human or leader must decide, wherever supported by available data. Keep that information consistent in Needs attention and All. Never guess missing facts or use a new agent/model to derive them. This interaction information is distinct from the summary of the task's purpose; it does not expand permissions or create a live narrative.

## Card content and interactions

Place the full title and summary at the top, with status/spinner beside the title and the remaining information below. Let cards grow and wrap at narrow widths. Do not truncate titles, add ellipses or line clamps, or substitute a tooltip/details page for complete content. Show the full available summary; its exceptions are defined below.

Retain all existing list information except monetary costs, respecting current availability and capability conditions:

- Status, workflow, and GitHub reference/status/hover information.
- Token IN/OUT and existing total fallback, branch, and change statistics.
- Time/age and scheduled-resume time.
- CPU/memory, including live-versus-recorded semantics.
- Queue position, read/unread, and pinned indications where applicable.

Do not invent unavailable metadata for existing tasks or plans. Execution tools/models and attention information are additional required fields under their rules below. Existing operations and accessibility must remain usable; retaining information does not require retaining the old table layout.

### Workflow and GitHub references

Show the full workflow name. If unknown, show **Workflow not specified**, replacing it with the actual name when available, consistently in every tab.

Show every associated Issue and PR separately, including several of either type. Each reference has visible Issue or PR text and its number when known, for example Issue #123. Wrap onto further lines without truncating or hiding references behind a count. Color or hover alone is insufficient identification. Preserve existing status, hover, and conflict interactions without inventing a known status.

Clicking the card opens task details. A valid HTTP(S) reference opens GitHub in a new tab without opening task details. Missing or non-HTTP(S) URLs remain non-clickable labels. Embedded controls perform only their own actions, without triggering card navigation.

### Execution tools and models

Show readable tool and model names on every card, for example Claude Code, Codex, or OpenCode. Preserve each tool–model association. These describe execution, not the naming model; no account/profile display is required.

Show all pairs actually used across steps and continuations, retaining earlier pairs after changes and completion. Normalize repeated identical pairs without purposeless duplicates. Do not guess missing identities/history or claim incomplete data is a complete history.

Before execution, show all known selected workflow pairs with **Planned**. Remove that label from each pair only when it actually starts working. Other unused planned pairs retain it regardless of the task's status/tab. Used pairs remain visible without Planned. Configuration alone is not evidence of use.

### Variant groups

Each variant has its own full card in its status tab and All, with a shared-group indication and access to comparison. Do not collapse a group in a way that hides individual variants or their information.

Determine relationships and actual comparison/selection readiness from group data, not only the current tab/search subset. Siblings in other tabs or outside search results must not by themselves remove relationship/comparison access. Preserve actual readiness conditions: the existing terminal set includes review and failed and is not equivalent to Finished.

Preserve the separate comparison screen, per-variant details and expandable diffs, winner-selection gate, and existing confirmation explaining removal of other worktrees/branches. Preserve review of the winner and navigation to its task. These requirements change the entry presentation, not comparison/selection semantics.

## Task summary lifecycle

The summary is a short explanation of the task, its goal, and intended work in very simple English. “Additional description” and “short description” refer to this same field. It is distinct from the title and from attention/activity information. One or two sentences is guidance, not a hard cap.

When generation is enabled, generate the summary at task addition, including leader plans, so it is visible in Planned. Extend the existing naming call to return title and summary together, using its existing runner/model selection without an additional agent or separate summary-only creation call. Provide enough task content to describe the goal accurately; no new arbitrary length cap is approved.

Automatically update the summary only after goal/content changes, never for status, progress, or ordinary turn-end/live-title refresh. Do not analyze work activity for it or generate a live narrative. User-triggered retries below retry summary generation, never task execution.

| Case | Required presentation and behavior |
| --- | --- |
| Successful generation | Show the full summary. |
| First generation fails or returns no summary | Task start is not blocked. Show Summary unavailable and a retry-generation action. No unbounded automatic retries. |
| Goal/content update is generating a replacement | Keep the previous summary without a stale/out-of-date label; replace it when ready. Pending alone does not show a failure signal. |
| Replacement generation fails | Keep the previous summary, with a small, discreet, understandable signal that the summary update failed and can be retried. Do not imply task-execution failure. Exact icon/copy is a design detail. |
| Generation deliberately disabled, no summary | Preserve existing title selection with full wrapping. Omit summary space entirely, without blank space, error, or retry. Do not bypass the setting. |
| Generation deliberately disabled, summary exists | Keep it visible without automatic updates. Disabled generation is not a failure. |
| Pre-deployment task has no summary | Omit the summary; no unavailable placeholder, backfill, migration, lazy generation on display, or mandatory retry is required. Missing summary does not block the task. |

All generation retries are mutations and blocked offline. The disconnection notice remains required even though pending summary replacement has no stale label. The existing naming switch applies to the new summary; a separate generation path must not evade it.

## Search, ordering, and archive controls

Arrange the page as tabs with counters, then search and selected-tab actions, then the card grid.

### Search and counters

Search the selected tab by title, summary, Issue/PR number, workflow, execution tool, and model. Tool/model matching covers all used pairs shown on the card, including earlier steps/continuations. All searches across statuses within the project and includes archived matches only when Show archived is enabled.

Retain the phrase across the five tabs and apply it immediately after switching, without retyping or Enter. Clear it on project change, including returning to a previous project, and on application restart. Clearing the phrase must not reset remembered per-project tabs.

Every tab counter reflects matching tasks in its eligible set, including inactive tabs. Clearing the phrase restores full eligible counts. All counts each eligible task once, including individual variants. Search and status updates do not navigate to another tab. No extra filters or cross-device synchronization are required.

### Existing ordering and queue positions

Retain `sortRuns` ordering after eligibility and search: non-archived pins first, then existing status weight (waiting, review, running, scheduled resumption, queued, done, failed, cancelled). At equal weight, scheduled resumes use earliest `autoResumeAt`, queued tasks oldest `createdAt`, and other ties newest `createdAt`.

Pinning changes ordering, not classification or execution. Queue positions use the entire non-archived queued set in creation order, unaffected by search or card order. Archived tasks have no pin control or pin priority; archiving retires a pin. Plan-only records need a deterministic technical extension of existing ordering, not a new business sort.

### Archive action versus visibility

The archive-finished action appears only in Finished and All. It affects all tasks classified as Finished in the current project regardless of search/filters, including hidden results. It excludes active tasks and unresolved failures requiring attention. Align the existing archive selector with this classification; merely having a failed record is insufficient.

Before executing, show a confirmation explaining that all completed tasks in the project are covered regardless of filters. Confirming performs the operation; cancelling or closing does nothing. Do not imply active tasks are included. Exact copy and an optional count are design details.

**Show archived** is a separate visibility toggle, available only in All and off by default. It adds archived tasks to All under the current search phrase and counter rules; switching it off hides them. It neither archives nor restores tasks. The other four tabs never show archived tasks. Archived cards retain all required information, including tool/model history.

## Loading, empty results, and disconnection

| State | Required behavior |
| --- | --- |
| First data fetch pending | Show Loading tasks. Do not show an empty-list result. |
| First fetch fails | Show a readable error and Try again. It retries the data fetch, not task execution. |
| Loaded tab has no eligible tasks | Show “No tasks in this tab.” |
| Search has no matches | Show “No matching tasks.” and Clear search. Clearing restores eligible results/counts without switching tabs; if still empty, show the empty-tab message. |
| Connection lost after data was available | Retain last available data, clearly indicate possible staleness, and stop card work spinners in all tabs, including after switching. Keep last known statuses; do not infer completion or change backend status. |

Offline, allow browsing/filtering available retained data but block task-changing actions, including resume, archive, Close without retry, and summary retry. Retrying a data read does not relax mutation restrictions. Loading/failure is not evidence of no tasks or no search matches.

## Technical follow-ups and handoff

The business requirements are sufficient for team handoff. No additional business decision is currently required. They are not a finished engineering design or implemented feature.

1. Define plan-only storage/source and dependency-start wiring, with deterministic ordering. Do not require a pre-existing run or silently drop these tasks.
2. Define classification and explicit-closure recording under the existing contract rules. Preserve scheduled-resume precedence and archive scope; do not introduce backend state changes merely to render tabs or handle disconnection.
3. Verify actual whole-task activity signals and effective tool/model history across creation, steps, continuations, and recovery. Handle missing data truthfully; never substitute model analysis or configured selection for evidence.
4. Extend naming output and the goal/content update path, respecting the disabled switch. Reconcile source/title caps, protect summary from live-title refresh, and implement the distinct failure/legacy cases.
5. Wire tab memory, search lifetime, counters, live movement, offline restrictions, and group access without changing preserved operations or leaking changes to global Tasks.
6. Complete responsive layout, keyboard/accessibility behavior, focus/scroll handling, and routine copy. Preserve full content, explicit labels, and interaction separation. These are design tasks, not new approval gates.
7. Validate the acceptance criteria with meaningful cases: long content/narrow screens, representative task volumes, status transitions, partial data, all summary cases, cross-tab variants/search, offline behavior, and project isolation. Follow root AGENTS.md for implementation and regression checks.

If technical investigation reveals a concrete conflict with these requirements, report it before changing behavior. Unrequested extra filters, synchronization, or reapproval of existing operations are not prerequisites. This document-only delivery changes no code, configuration, Inbox document, or runtime state.
