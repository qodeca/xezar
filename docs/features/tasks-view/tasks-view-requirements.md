# Tasks view — business requirements

Date: 9 September 2026  
Business stakeholder: Marcin Obel  
Status: Not ready for implementation — agreed direction with blocking business decisions; not an implementation specification.

## Purpose

Make it easy for an ordinary user to understand what is happening with tasks: what is planned, what is working now, what needs a response, and what has finished. The view must explain each task clearly without requiring the user to open it just to understand its purpose or read its complete title.

This document records the supplied conversation decisions and checks them against the current repository. Existing code is evidence of current behavior, not proof that a new product decision has been agreed.

## Agreed organization

The view has five tabs: four status categories and an additional tab covering all task statuses. The agreed order is Planned, Running, Needs attention, Finished, All: All is the last, fifth tab. On the first visit to Tasks for a project, open Running. On subsequent visits, restore the last selected tab separately for that project. English labels, including All, are proposals; the meanings are agreed.

Marcin explicitly decided to use a unified card presentation in all five tabs, including Finished. Complete titles and available summaries are shown in every tab; the agreed unavailable-summary cases below are exceptions to requiring summary text.

| Order | Proposed label | Business meaning | Presentation |
| --- | --- | --- | --- |
| 1 | Planned | Tasks with a concrete decision to execute that are waiting for their start conditions: queued work, leader-planned tasks not yet started (including tasks waiting for dependencies), and valid scheduled automatic resumption. Excludes tentative backlog ideas. | Cards |
| 2 | Running | Tasks currently doing work, including waiting for tests or a subtask without needing a human/leader decision; show a waiting indication in that case. | Cards |
| 3 | Needs attention | Tasks needing help, a decision, or interaction from a human or leader. Includes tasks that ended with an error and still need a retry or closure decision. | Cards |
| 4 | Finished | All finished tasks, including cancelled tasks clearly marked Cancelled without implying success. Also includes failures explicitly closed without a retry, preserving the error and marking closure without a fix. Archive treatment remains unresolved. | Cards |
| 5 | All | All tasks in scope regardless of status; archive inclusion remains open. Same logical tasks, not duplicate runs. | Cards |

Planned includes a leader's task that has not yet been started or entered the technical execution queue, when execution has been decided and the task is waiting for its start conditions. For example, a task planned to execute automatically after two preceding dependency tasks finish belongs in Planned while it waits, and must start automatically when those dependencies have completed and its start conditions are met. An exact date is not required for dependency-based work. Loose backlog items such as “maybe someday,” without a decision whether or when to execute and without priority, are excluded. The criterion is a concrete execution decision and waiting for start conditions, not simply having a backlog entry.

This is a required business outcome, not a claim that the current engine already supports leader plans or automatic dependency-based starts. The plan source, data representation, and start mechanism require technical specification. It does not bring the future external-leader MCP integration into scope.

A task that ends with an error requiring a human or leader to decide whether to retry it or close it belongs in Needs attention. Usage-limit stops with valid automatic resumption scheduled follow the exception below. An error must not disappear into Finished merely because execution has stopped.

When an agent has finished its work but the result requires review and a decision to approve it or send it back for correction, the task belongs in Needs attention without a work spinner. The reviewer may be a human or an AI leader. This resolves the UI classification of `review`; it does not change when the review gate runs or who is permitted to approve or request corrections.

When an agent is waiting for tests or a subtask to finish and needs no decision from a human or leader, the task remains in Running with an indication that it is waiting. The spinner remains visible when those tests or subtasks are actually working: activity means the whole task, not only its main agent. For example, a main Claude Code agent waiting for its own working subagents still represents an active task. The monitoring mechanism is unchanged.

Cancelled tasks belong in Finished, clearly labelled Cancelled, with no work spinner and no indication that the task succeeded. Cancellation is distinct from archiving or explicitly closing a failed task.

After an explicit decision by a human or leader that a failed task will not be retried, it moves to Finished. Preserve its error information and history, and clearly mark that it was closed without a fix; the exact English label is not yet agreed. Do not imply success. This closure is distinct from cancellation, archiving, or marking the task read. Its placement and retained error information are agreed; the way to invoke closure and record the decision still needs specification.

Marcin confirmed that the existing automatic-resumption mechanism is retained, with no engine change. Among usage-limit stops, Needs attention contains only cases where automatic resumption is unavailable because the information needed to resume is missing. Tasks waiting for valid scheduled automatic resumption (`autoResumeAt`) belong in Planned, with the resumption time visible on the card and no work spinner while they wait. They do not belong in Needs attention or Running during that wait.

### All statuses and page layout

The additional tab (proposed label All) shows all tasks within the Tasks scope regardless of status, using the same full cards and information rules. It presents the same logical tasks as the status-category tabs; it does not create copies of runs. Tentative backlog ideas remain outside Tasks. “All statuses” does not settle archived-task inclusion: archive is a separate flag and its visibility remains open.

Search filters the currently selected tab. Preserve the search phrase when switching tabs and apply it immediately to the newly selected tab's results, without retyping or pressing Enter. In All, this filters tasks across all statuses within its eligible scope. When a search phrase is present, counters on all five tabs show the number of matching tasks in each tab, including tabs that are not selected. Clearing the phrase restores each tab's full count within its eligible scope. All counts logical tasks once within All; its overlap with category tabs does not create duplicate tasks. The exact fields searched, phrase persistence across restarts or projects, and archive eligibility remain open. Sorting follows the existing rules described below.

The agreed page arrangement is tabs with counters, then a search field and actions for the selected tab, then a grid of task cards. The archive-finished action is available only on the last two tabs, Finished and All; it is not available on Planned, Running, or Needs attention. It archives all tasks classified as Finished within the applicable project/view scope, regardless of search text or filters, including completed tasks hidden by those filters. Offering it in All does not make active tasks or unresolved failures requiring attention eligible. Cross-project scope and archived-task visibility remain open. Counters follow the search phrase across all tabs and return to full eligible counts when it is cleared. Other action details and any interaction with filters other than search still need specification. All is the last, fifth tab. The first visit for a project opens Running; subsequent visits restore that project's last selected tab. Status changes never switch the selected tab automatically. Cross-device synchronization and global Tasks behavior remain open.

When a task changes status, update its category membership and the tab counters automatically while keeping the user on the currently selected tab. Preserve the search phrase and continue applying it to results and all tab counters. In All, update the same logical task's status rather than creating a duplicate. Focus and scroll details remain to be designed; this requirement does not prescribe an arbitrary focus or scroll change.

Before archive-finished executes, show a confirmation dialog explaining that it will archive all completed tasks in the applicable scope, regardless of the current search text or filters. Only explicit confirmation performs the operation. Cancelling or closing the dialog archives nothing. The dialog must not suggest that active tasks are included. Exact wording and whether to display a count N are UX proposals to finalize, not agreed requirements. This confirmation requirement does not decide archived-task visibility or approve a show-archived control.

### Ordering and queue positions

Preserve the current task ordering in every new tab after selecting its eligible category and applying search, including pinned tasks first where current pin semantics apply. Reuse `sortRuns` in `packages/web/src/lib/task-groups.ts`; do not invent a new date ordering. The existing comparator prioritizes non-archived pins, then status weight (`waiting`, `review`, `running`, scheduled automatic resume, `queued`, `done`, `failed`, `cancelled`). At equal weight, scheduled resumes use the earliest `autoResumeAt`, queued tasks use oldest `createdAt` first, and other ties use newest `createdAt` first. Pinning changes ordering, not the agreed category membership.

`queuePositions` in that same file uses the complete non-archived queued set in creation order. Search, card sorting, or pinning must not renumber the execution queue or change the engine's order. `TasksOverview` currently calls `sortRuns(filterRuns(all, query), view)` and separately `queuePositions(all)`; preserve this separation.

Preserve archived pin semantics: the current archived view ignores pin priority and withholds the pin control; archiving retires a pin. Do not introduce pinning for archived tasks. Their visibility remains a separate open decision. Leader plan items without run records may require a deterministic technical extension of existing ordering; specify that extension rather than invent a new business ordering.

## Agreed information and readability

### Complete content

- Always show the complete task title on cards in all five tabs, including Finished. Wrap long titles; do not truncate, add ellipses, or apply a line clamp. A tooltip or opening the task is not a substitute for showing the title in full on a card.
- Show the full task summary on each card in all five tabs, including Finished, when available. Pre-deployment tasks without one omit the summary section/text, without a required placeholder or retroactive generation; new generation failures use their agreed fallback and retry action.
- Present the required information in full and allow the layout to grow with its content. This applies at narrow screen widths too.
- Use the same card presentation and complete-content rules across all five tabs. Finished is covered by this agreed requirement.

### Agreed card layout

Place the complete title and short summary at the top of the card, with status and the applicable spinner beside the title. Arrange the retained information from the current list beneath them. The spinner follows the agreed actual-activity rules. This structure is agreed; detailed spacing and styling can follow it without truncating content.

### Task summary

New tasks need a short summary in very simple English, suitable for an ordinary user. Pre-deployment tasks without a summary follow the explicit legacy exception below. It explains what the task is, its goal, and what it should do. The term for the previously discussed short description is **summary**. It describes the task's purpose, rather than narrating its latest activity.

The summary is generated automatically when a task is added, including a leader-planned task, so it is already visible in Planned. Update it only when the task's goal or content changes. Do not update it from ongoing activity, work progress, or status changes alone, and do not analyze current work to produce it.

The agreed technical direction is to extend the existing title-naming model call so the same call returns both the title and a task summary in simple English. At creation, produce the title and summary together, without an additional agent or a separate summary-only model call. Reuse the existing runner/model selection rather than introduce a newly selected model. This is a direction to implement, not an existing capability.

Provide enough task content to describe the goal correctly; the current 500-character source clipping can omit essential intent and must be addressed. Goal/content changes update the summary. Ordinary turn-end/live-title updates must neither update the summary nor analyze activity for summary generation, even though the existing title refresh can use progress context.

If the model does not respond or summary generation produces no summary, the task may start normally. Show “Summary unavailable” on the card with a user action to retry summary generation. Retrying generation does not restart or rerun the task, and this agreement does not introduce automatic unbounded retries. Handling a disabled namer and a stale summary after a goal/content edit remains to be clarified. Existing title truncation also needs technical reconciliation with the full-title requirement; this document introduces no new arbitrary length limit.

Pre-deployment tasks without summaries are left as they are. Omit the summary section/text on their cards; no “Summary unavailable” placeholder is required for this legacy absence. The missing summary does not block the task. No backfill, migration, retroactive summary generation, or generation on card display is required. The proposed lazy generation on viewing a card is rejected. The retry action agreed for a failed new generation remains, but is not a mandatory action for legacy missing summaries. This is an explicit exception to the summary requirement, not an outstanding migration decision.

One or two sentences is a writing suggestion, not a strict length limit. Clarity and completeness take priority over an arbitrary sentence or character limit. The summary is separate in meaning from the title; the existing generated title (`titleSummary`) is not automatically an adequate task summary.

### Status and work indicator

- Show a simple status based on existing task data. Computing or displaying it must not require a model.
- Show a small spinner only while the task as a whole is actually working, including its tests and subagents even when the main agent is waiting. Waiting for a response, being queued, or having ended in an error is not itself evidence of active work.
- Do not generate a live activity description using another agent or model. Marcin explicitly rejected this because of the additional overhead.
- A task stopped by a usage limit has no work spinner, including when automatic resumption is scheduled. A future start time is not actual work; the spinner appears only when work actually resumes.
- A task awaiting review or an approval/correction decision from a human or AI leader has no work spinner after the agent has finished its work.
- A cancelled task in Finished shows Cancelled, has no work spinner, and must not be presented as successful.
- A card for a task waiting for valid scheduled automatic resumption appears in Planned and visibly states when work is scheduled to resume. The resumption time must be readable on the card without opening the task or hovering.
- Waiting for tests or a subtask without needing a human/leader decision is shown in Running with a waiting indication. Show the spinner when that downstream work is actually active. The monitoring status alone is not evidence of work, and existing animated status dots must not be copied as the spinner rule. Verify which non-model activity signals the backend actually provides; missing activity data is a technical gap to resolve, not permission to invent activity or use model analysis.

### Workflow and GitHub reference

- Each card shows the current workflow.
- Show the associated pull request or GitHub issue prominently and legibly when present. Its type must be identifiable from visible text, not color alone: show Issue or PR and the number when known. Recognizing the type must not require hovering. Suggested formatting is “Issue #123” and “PR #456”; the exact formatting is not prescribed. When a task has both a related GitHub issue and a PR, show both on the card, each with its visible type, number when known, and existing link behavior.
- Preserve the existing `TaskReferenceChip` / `ReferenceChip` link and interaction behavior: a valid HTTP(S) reference opens the linked GitHub page in a new browser tab; preserve existing status information and hover behavior.
- A reference without a URL is a non-clickable label. Preserve the existing guard that also makes non-HTTP(S) URLs non-clickable.
- Do not invent a reference or imply a known GitHub status when none is available.
- The visible type requirement takes precedence over literal badge appearance: the current PR badge showing only a number without the word PR does not meet it. Preserve status and hover information while adding the required visible identification.

### Cost information

Do not show monetary cost amounts on the new Tasks cards in any of the five tabs. Marcin considers those amounts unhelpful because the team uses local models and subscriptions rather than per-token billing. This is a presentation decision for the new Tasks view only; it does not remove backend measurements or stored cost data, or change cost information in other views. Token counters are retained under the information-preservation decision below.

### Preserve the current list information

Marcin explicitly decided that all other information currently displayed in the task list must be carried into the cards, except monetary cost amounts. Retain the following according to the current data availability and applicable display conditions:

- Status and workflow, with the newly agreed tab and spinner rules.
- Token usage (IN/OUT and the existing total fallback), branch, and change statistics.
- Time/age information and scheduled-resume time.
- GitHub reference and its existing status/hover information.
- CPU and memory information, including existing live-versus-recorded semantics where applicable.
- Queue position and read/unread and pinned indications where applicable.

These are existing information categories, not new metadata requirements. Preserve truthful missing-data and capability handling; do not invent values for tasks or leader plans that lack them. Token, branch, and change-stat visibility are no longer open inclusion questions. The full title, full short summary, five-tab organization, and agreed spinner meaning take precedence over the old presentation. Preserving information does not mean copying the table layout, its truncation, or its column arrangement. The agreed structure places full title/summary at the top, status/spinner beside the title, and the retained information below.

## Implementation readiness review

**Not ready for implementation.** The five-tab card presentation and scheduled-resume placement are clear, but the team cannot derive complete expected behavior from the current agreements. AC-01–AC-33 cover the agreed subset; they do not close the open questions.

Blocking business decisions are the project/global/sidebar scope (question 6), archive visibility and the remaining closure interaction/label/decision-recording details (2–3), disabled-namer/stale-summary behavior (4), and the user-visible behavior of operations, attention information, navigation, and view states (5, 7–9). Cancellation is resolved as Finished, clearly labelled Cancelled without a spinner or implication of success. Explicitly closing a failure without retry is also resolved as Finished, retaining the error and marking closure without a fix; its invocation, exact label, and decision recording remain to be specified. Waiting for tests/subtasks without a human/leader decision is resolved as Running with a waiting indication and a spinner while downstream work is actually active. The spinner meaning is settled; proving activity from available backend signals remains technical work. Review classification is resolved as Needs attention without a spinner. Inclusion of concretely planned leader tasks before a run exists is now agreed, including automatic start after dependencies; tentative backlog is excluded. Final labels (1) also need confirmation before final UI acceptance. Resolve these as business outcomes; do not ask Marcin to choose implementation details.

The development team can choose component composition and reuse, layout techniques, event/cache wiring, data representation and persistence, and test tooling within repository rules and the agreed outcomes. It must verify available activity signals and specify truthful handling of missing data without model analysis; this document does not claim that every backend already exposes downstream activity. It must specify the source and representation of leader plans and how dependency completion triggers a planned task; existing support for this has not been established. Summary generation must extend the existing title-naming call, using its existing defaultRunner/namerModel selection without an additional agent. The team must specify the combined response and purpose-only update path, prevent ordinary live-title refresh from updating summaries, and reconcile the current 500-character source clip and 40-character title cap/postValidateTitle with accurate intent and full-title display. These are implementation details still to solve, not claims of existing support or permission to add an arbitrary cap. Likewise, rendering many cards is a technical concern; changes to what users can access or how they navigate the results need an agreed user experience. These choices must preserve full content, the existing automatic-resumption engine, and the exclusion of model-generated live activity descriptions.

- The previous idea of cards above a list, with a Completed/All switch, was superseded by the tabbed card view. The later addition of All is a fifth card tab, not a return to that earlier switch or list.
- The earlier normal-list presentation for Finished, and the open proposal about full titles in that list, were superseded by Marcin's explicit decision: all five tabs use unified cards with complete titles and complete short summaries.
- A generated live activity narrative is explicitly excluded. A plain status from existing data is accepted.
- An external leader's MCP integration, discussed for the next release, is context only. This feature does not implement that integration or specify its protocol. Leader-planned tasks still belong in the business definition of Planned.
- No new executor field, responder field, lifecycle state, new summary model selection, or archive policy is approved by this document.
- Omitting monetary cost amounts from Tasks cards does not remove backend cost measurements or stored data, or change other views. Existing token information is retained according to current data availability and capability handling.
- Tentative backlog items without a concrete execution decision are excluded from Planned. Requiring an existing run, queue entry, or exact date for every Planned task would contradict the agreed inclusion of dependency-based leader plans.
- The earlier assignment of all usage-limit stops to Needs attention, including scheduled automatic resumption, is superseded. Only usage-limit cases lacking the information needed for automatic resumption require attention; tasks waiting for valid scheduled resumption belong in Planned, with the resumption time visible and no work spinner.
- Disabling automatic resumption or requiring a human/leader to resume every usage-limit stop is excluded. Preserve the existing mechanism without an engine change.
- Classifying review as Needs attention does not change review-gate activation rules or approval/correction permissions. Showing tests/subtask waiting in Running does not change the monitoring mechanism; its spinner reflects actual activity across the whole task, including downstream work, rather than monitoring status alone.

## Acceptance criteria

These criteria cover agreed behavior. Cases identified as open above need decisions before final implementation acceptance; the document does not resolve them by assumption.

| ID | Scenario | Expected result |

The first visit for a project opens Running; later visits restore that project's last selected tab. Tabs have counters, followed by search and selected-tab actions, then a card grid. Final English labels follow the wording decision. |
