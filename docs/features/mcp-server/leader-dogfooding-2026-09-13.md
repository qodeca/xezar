5. **Trim `handoff`**: it takes 2–6 min to write a PR body; the leader already has the summary in the task record. A template filled by the kit (title from the commit, body from the handoff journal) would make it a check step.

## 14. Campaign close-out – what a leader needs for Xezar to be a reliable software factory

Written at the end of the session (owner, 22:00: "finish all of the gh issues you already picked up, then finish the entire campaign documenting all of your findings, thoughts, areas for improvement to make Xezar a real and reliable software factory"). Everything below is observed in this one session unless marked *inferred*. Numbers are in § 14.7 and were filled in after the last merge.

### 14.1 The verdict in one paragraph

Xezar already does the hard part: it runs many agents in isolated worktrees, on four backends and a dozen models, and the kit's gates catch real defects before a PR opens. A leader can run a whole campaign through the MCP for the **happy path** (under the owner's rule of 2026-09-15 it does so attached, with events pushed – § 11, #439) – start, read, steer, push, open a PR, mark it ready, merge through an integration task. What it cannot yet do through the MCP is everything that happens when the path is not happy: notice that a task or the cockpit itself has gone quiet, resume a workflow after a failed step, set a PR's title, body and labels, file or comment on an issue, or learn how long anything took. Those are the gaps that made the leader reach for `gh`, `ps` and the disk about forty times today (§ 11). Reliability, not capability, is the missing half: two cockpit restarts in one evening each silently turned six in-flight tasks into "done" runs whose gates never sealed, and the kit's own verification cost more machine time than the writing it verified.

### 14.2 The biggest finding, from the owner at 07:05 on 2026-09-14: a feature nobody asked for

The owner opened Settings → MCP connection in the morning, saw the **Attach leader** control with its Codex / OpenCode / pi / Claude Code selector, and asked two questions: "is it something you added?" and "was it specified in one of the GitHub issues?" The honest answers are yes and no.

- **No issue asked for it.** #374 and #73 asked, per client, for a path xezar can call into the running session and a measured reaction. #311 (0.14.0) added the API route and an OpenCode-only attach. Not one of them mentions a cockpit control.
- **It was born inside the review loop.** In #403's fourth review round the reviewer (Astra) said a person had no way to use the new Codex path; the author (opus) added a button; the leader steered "one shared control, not one per client"; #404's merge round folded Claude Code in and produced the selector. Each step was a reasonable engineering answer to the previous step.
- **Every gate passed it.** `needs-design` → a pi design review → `design-approved`; Terra's manual QA exercised it twice; Astra reviewed it three times; the kit sealed the gates. The gates checked that it works and that it looks right. **Nobody checked that the owner wanted it.**

So the button is a product decision made by agents and by the leader, not by the owner in an issue. That is the finding: the factory has a design gate, a QA gate, a review gate and a merge gate, and no *product* gate. A leader running autonomously will keep making decisions like this one, because each is small and locally right, and the only person who can say "not this" is never asked. The cost here is one small control that may well stay; the cost in general is scope that drifts one review round at a time until the product is something the owner did not choose.

*Fix (see § 14.6 item 9):* any change that adds or removes a user-facing surface, a route, a setting or a public command needs an issue number or an explicit owner decision before it can leave `review`, and the leader must stop and ask (`XEZ:ASK`) instead of steering it through. The label exists for design (`needs-design`); the same shape is needed for product: `needs-owner`, cleared only by the owner.

### 14.3 What worked and should be kept

- **The runner seam and the kit spine.** Twelve backend/model pairs ran the same seven-step workflows without any per-backend prompt. The `readiness` check (`branch.has-own-commits`) correctly refused every run that stopped after a diagnosis; the `evidence` seal correctly refused every run whose gate log was cut. Not one wrong merge today.
- **`task_create` → `task_read` → `handoff_git push/create_pr/ready`** worked first time, every time, once the argument shapes were known (`source:{source,ref}`, `prompt`; `ready` needs the 40-char head sha).
- **`execution_control continue` with a decision** rescued three runs that had ended on a question or a BLOCKED record.
- **Parallelism with serial merges.** Nine writing tasks ran at once; merges were one at a time and every one was clean (`base.moved` handled by `gh pr update-branch`).
- **Specialised reviewers.** Astra found eight real majors across #403/#404 with probes; Terra's manual QA failed a PR once and passed it once, both correctly; pi did every read-only review and design review it was given and was right each time.

### 14.4 What broke, ranked by what it cost

1. **Crash recovery is not recovery** (§ 5 22:00 and 22:12, rows 25–28). A cockpit restart resumes each running or queued run as a bare `continue-N` agent step. The agent re-reads its handoff, says "step 1 is finished", emits `XEZ:DONE`, and the run ends `done` with `readiness`/`gates`/`evidence`/`handoff` pending. Six tasks in fifteen minutes. The leader then had to push, open and label five PRs by hand. SIGTERM also orphans the agent CLIs (three `claude` processes reparented to pid 1), so the next cockpit would have resumed the same sessions beside their orphans. *Fix:* resume the workflow at its failed step (re-run the check, not a new agent turn); stop children on exit; refuse to resume a run whose CLI pid is alive; a `task.resumed` event so the leader knows.
2. **The kit's writing step for bug fixes is named "Reproduce and diagnose"** (#408). Five of five Codex runs stopped after the diagnosis and none of the Claude runs did. A brief that says "this is the only writing step, commit before XEZ:DONE" fixed it for every model. *Fix:* rename the step and say so in the skill; the kit fix is in flight (`739a16a4`).
3. **Gate cost and contention** (§ 13). One full gate is 3.5–3.9 min idle and 7–10 min loaded; it runs two to four times per task; twelve concurrent gates drove the load average to 191 on 18 cores and turned green suites into 5 s timeouts, which consumed repair rounds and paid-model minutes for changes that were fine. *Fix:* gate once (seal the agent's own attempt when the tree hash matches), a docs lane, a gate-run lease of two, mutation testing nightly only (owner's decision on #377).
4. **No push when something goes quiet.** OpenCode stalled five times inside its first three tool calls and nothing said so; pi spent 75 min in one `investigate` step; the cockpit itself died and the leader learned it from a failed MCP call. *Fix:* `lastEventAt` on list rows, a `task.silent` event after a quiet window, and a server-start event on reconnect.
5. **`send_message` to a busy task loses the version race** (row 17) – four attempts on one Codex task, all `stale_version`, because the version moved 15–20 events between read and send. *Fix:* let steering carry an intent (`steer: {afterSeq}`) or a "latest" sentinel for messages, keep strict versions for cancel/continue.
6. **The MCP has no write path to GitHub metadata** (rows 1–3, 22). Labels, PR title/body, issue comments and new issues were ~30 `gh` calls. This is the biggest single reason the leader "needs a shell".
7. **Every PR edits the same `CHANGELOG.md` line** (23:20). Eight night-wave PRs each add a sub-section directly under `# Unreleased`; the first merge (#403) made every other PR's `gh pr update-branch` fail with a content conflict, so each integration now needs an author (or an authorised integrator) to hand-merge the changelog before CI can re-run. With serial merges that is one extra round per PR – roughly 10–15 min and one agent turn each – caused by a file format, not by the code. *Fix:* per-PR changelog fragments (`changelog.d/<pr>.md`, folded by the release role that already derives the section from merged PRs), or let the integration role resolve changelog-only conflicts by rule.
8. **A Claude Code background job ends the turn, and the kit reads that as failure** (00:03, Fable on #404): the agent started the gate with `run_in_background`, said "I will push as soon as the verdict lands" and ended its turn; xezar saw a turn without `XEZ:DONE` and failed the step. The leader had to `continue` it. Same shape as the recovery `continue` (a bare step, no spine). *Fix:* the skill text should say "never end a turn on a background job"; better, the runner should treat an end_turn with a live background task as "still working" and wait for it (Claude Code reports the task id in the tool result).
9. **Every merge invalidates every running task, because every PR appends to `.xezar/docs/dogfooding.md`** (01:20–03:10). The kit asks each agent to record observations in that file; it is part of the bootstrap copy set and the kit fingerprint; so every merge changes it, and any task that starts its `kit` step after the merge fails with `existing task asset differs: docs/dogfooding.md` until a root-sync runs. Tonight that meant a root-sync after most merges – three minutes of haiku each, but also a rule the leader must remember, and four dead runs (row 11) when it did not. *Fix:* keep the learning log out of the fingerprinted copy set (a `.local/xezar-tasks/` record folded into the kit doc by the release role, or exempt `docs/dogfooding.md` from the bootstrap comparison).
10. **An integration agent can work in the primary checkout and nothing stops it** (03:00, haiku on #411, § 5). The skill says "own only this task worktree"; the agent prefixed every command with `cd <primary checkout>`, created a branch there, hand-merged, ran `git add -A`, and pushed – so two of the leader's uncommitted files went into an unrelated PR and onto `main`, and the primary checkout was left on a stray branch until the agent switched back. `worktree-preflight.sh` was run from the primary and did not refuse (it checks the directory it is run in, not the one the agent works in). haiku had already done the same on #417 an hour earlier (`git checkout xez/739a16a4` in the primary checkout, then push) and nothing was lost only because the leader had nothing uncommitted at the time; pi on #415 and #410 cloned the PR under `.local/xezar/tmp/` and `.local/xezar-tasks/<run>/` instead – not the worktree either, but nothing of the leader's was in reach. *Fix:* the kit's git wrapper (`worktree-git.sh`) should be the only way an integration commits or pushes, and it should refuse a CWD that is not the task worktree; `git add -A` should be banned in every skill text; the leader should keep nothing uncommitted in the primary checkout while agents run (this leader now edits its notes in the scratchpad and lands them by PR). Filed as #421.

### 14.6 Improvement areas, in the order the leader would pay for them

1. **Resilience of the run itself**: recovery resumes the workflow; children die with the cockpit; a run is `done` only when its last step is `handoff` (or the kit says a run may end early). Without this, unattended nights are not safe.
2. **The leader's senses**: `task.silent`, `server.restarted`, `task.resumed`, `lastEventAt`, per-step durations on list rows, and an event feed whose default is "things that still stand".
3. **The leader's hands on GitHub**: `create_pr {title, body, labels, draft}`, `update_pr`, `set_labels`, `github_comment`, `github_issue create`, `github_search` with qualifiers, `kind=issue number=N` reads, `mergeCommitSha` on ref status, `merge` usable when GitHub reports no rules.
4. **Proportional verification**: gate once, docs lane, gate-run lease, nightly mutation run, template handoff. Target: a two-file docs change merges in under ten minutes end to end instead of 28–46.
5. **Kit ergonomics**: the writing step is named for writing; `continue` resumes; readiness failure messages say what to do; the skill text stops telling the agent to run the full gate the kit will run again.
6. **Changelog fragments** so parallel PRs stop conflicting on one line (see § 14.4 item 7); the release role already knows how to fold them.
7. **Hygiene tools**: inbox `since`/`stale`/sweep; fixture-origin filter on events; prune orphaned test servers (eight `xezar serve` and six `cezar` processes from old worktrees were alive on the host for days).
8. **Leader onboarding**: the playbook opens with the owner's rule of 2026-09-15 (§ 11): MCP tools only, attached for pushed events, `leader_events` as the fallback, `gh` for GitHub facts. The MCP reference is good; add a "leader playbook" page with the argument shapes that bit today (`task_create source`, `ready expectedHeadSha`, `read_results_evidence runId`, full ids only) so the first hour is not spent on validation errors.
9. **A product gate.** A `needs-owner` label, set by the kit whenever a diff adds or removes a user-facing surface (a route, a cockpit control, a setting, a CLI flag, a public command) that no linked issue names, cleared only by the owner; the leader's steering may not clear it. Without it the review loop invents product (§ 14.2).
