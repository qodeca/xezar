Two implementation notes that follow from the decisions and are load-bearing for Phase 3:

- **D-113's enforcement predicate is `holdsMcp`, not `kind`.** Exactly one catalog entry carries
  `kind: 'mcp'` (`claude.project.mcp`). `codex.project.config` and `opencode.project.config` carry
  `kind: 'settings'` and hold MCP blocks all the same; the catalog marks all of them
  `holdsMcp: true`. Keying the content-elision rule on `kind` would return credential-bearing file
  content for the codex and opencode project configs, which is exactly what the decision forbids.
- **D-128's write must go through `PATCH /projects/:projectId`.** The project's own
  `.xezar/config.json` `maxParallel` key parses but is **ignored by enforcement**; the registry
  entry's `maxParallel` is what narrows the cap. Writing the project-config key would look like a
  successful override and change nothing.

## The four project-section / global-effect mismatches — the leader's ruling

Recorded because section 3 warns that "a section URL does not determine all effects", section 8
repeats it, and Phase 3 reads this document as its enforcement input.

1. **Agent config `scope:'user'` files (I-112) are excluded.** M-16 excludes home-file
   administration even behind a project route. **MCP must refuse them by the catalog `scope` field,
   not by path matching** — a path test is defeated by symlinks, relocated agent homes
   (`agentHomePaths()`) and any future vendor path change, while `scope` is the catalog's own answer.
   The six entries are `claude.user.settings`, `claude.user.memory`, `codex.user.config`,
   `codex.user.memory`, `opencode.user.config`, `opencode.user.memory`, all `tracked: 'outside-repo'`.
2. **Provider enable/disable (I-115) is global — safe effective read only.** `disabledProviders` is
   workspace-wide, so the leader may learn that a provider is usable and no more (F-03, F-12).
3. **Agent-account selection (I-122) is global — effective read without identity.** Per D-122.
4. **Per-project `maxParallel` and tags (I-128, I-129) are project writes bound to this project.**
   **Project Remove (I-130) stays excluded**: it deregisters the project from the workspace registry
   and so destroys the leader's own binding — a leader must not be able to unregister its own project.

## Two recorded discrepancies between the requirements document and the current source

Neither is a defect in the source; both are places where section 6's operation-family names do not
match the symbols that exist. Recorded so a later reader does not grep for a name that was never there.

1. **M-05 lists "seen/unseen actions"; M-14 lists `getSkillsUpdate`.** Both families exist, but the
   real symbols are `markAllRunsSeen`, `markRunUnseen`, `setProjectRunRead` (I-016) and the
   `skillsUpdateRoutes` family at `packages/xezar/src/server/server.ts:2734` (I-093). `getSkillsUpdate`
   is the api-client function name (`packages/web/src/api/client.ts:1902`) for
   `GET /workspace/skills-update`, not a route name.
2. **M-18 lists `getAutomations, createAutomation, updateAutomation, setAutomationEnabled,
   checkAutomation, getAutomationCheck, getAutomationLog`** — it does not name
   `DELETE /automations/:id` (`server.ts:3364`) or `POST /automation-log/:receiptId/retry`
   (`server.ts:3448`), which exist as routes with no cockpit control (I-102). D-102 now exposes both,
   so M-18's list is narrower than the agreed MCP surface.
